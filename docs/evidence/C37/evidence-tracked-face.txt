=== [3b] 上面那条 staged 扫描的反事实，以及 [3] 那次读数为什么不算证据 ===
  复测采集: 2026-09-26 16:15:26 CEST MacBook Air dev b875430
  [3] 那格打印的「Finding 行数: 0」是用 `grep -c "Finding"` 数的，而 gitleaks 8.30.1 的输出里
  根本没有 "Finding" 这个词（它打 `WRN leaks found: N` 与 JSON 报表）—— 也就是说那个数在任何
  情况下都是 0，那一格不构成判据。真正的判定面是 exit code + JSON 报表里的命中项，重测如下
  （同一暂存集 = [3] 补进版本库的 10 份档案，命令 `gitleaks protect --staged --redact -f json -r -`）：

  $ gitleaks protect --staged --redact -f json -r -          # 暂存集 = 10 份补档，无探针
    staged files=10   exit=0   findings=[]
  ⇒ 补档不夹带凭证。再证明这条闸门「在这个面上会红」（假值探针，形似而非真凭证）：

  探针形态                  总长   exit   findings（逐字读数）
    github_token = "ghp_+35"   39    1     ['generic-api-key']
    github_token = "ghp_+36"   40    1     ['github-pat']
    github_token = "ghp_+38"   42    1     ['github-pat', 'generic-api-key']
  ⇒ 会红，且命中集合随探针形态变化（github-pat 的形如 ghp_[0-9a-zA-Z]{36} 要够长才落进正则）——
    「exit=1 但报表里少了一条规则」这种读数是真的，不是仪器坏了。本轮取第三行（两条都命中）作准。
  探针每次跑完立即 `git rm --cached` + 删除，三次与最后一次错用 flag 的跑法都未进过任何 commit；
  本档不含可复用凭证（探针值由固定字符池前缀截断拼成，不是随机生成的真 key）。

  采集过程另记两笔自己的错，因为它们正是「读数不算证据」的两种形态：
  ①第一次只测了一枚手工拼的探针就写下结论，长度口径（36/38 位）在档内前后不一致 —— 上面这张
    表是把 35/36/38 三个长度各测一遍得到的，取代那两句互相矛盾的叙述；
  ②中途用错过一次 flag（`-o` 不是 gitleaks protect 的选项）：
    exit=1   stdout=''   stderr="Error: unknown shorthand flag: 'o' in -o / Usage: gitleaks protect [flags] ..."
    —— 之前那句「exit=1 但报表为空」的读数就是这一次用法错误造成的，不是命中，已作废不引用。
  教训与本轮主线同形：**数的必须是判定面，不是顺手 grep 到的字符串**（台账里那条 evidence 也一样，
  在盘上 ≠ 在版本库里）。
