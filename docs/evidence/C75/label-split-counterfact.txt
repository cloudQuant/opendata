2. one of the four original claims was itself wrong, and what replaced it
--------------------------------------------------------------------------------
The first pass asserted that a positional SDMX key could not be substituted because _PATH_SEGMENT
"refuses anything that is not exactly one segment". That is false as written: the class is
[A-Za-z0-9._~\-] and contains the dot, so "0.0.0.0.4.0.0.0.M" is one legal segment. The real
absence is composition, not segmentation, and it has two measured carriers:

  - render_path fills each placeholder from getattr(query, name): one field in, one segment out.
    ParamSpec fields are name, kind, query_key, required, default, enum, note -- there is no join,
    derive or transform field, so a key assembled from several dimensions cannot be declared.
  - the OECD key form <flow>,<key> carries a comma, and _PATH_SEGMENT omits the comma exactly the
    way it omits the slash, so even a caller-supplied composite value is refused with
    *_PARAM_UNENCODABLE before any socket opens.

The entry therefore became flow.composite_key_segment, anchored on
    http_json.py:58   _PATH_SEGMENT = re.compile(r"^[A-Za-z0-9._~\-]+$")
with cross-anchor spec.py path_placeholders -- the validator that omits the comma, and the field
list that has no join.

A fifth label was examined and deliberately NOT split. symbol_normalization (1 row,
OBB2-tmx-EtfSearch) maps to columns.rename, which is present, and the split was rejected because
no transformation surface was read for it: the engine's rename publishes one declared key under
one declared name (key = column.source_key or column.name), and nothing in the row states that a
value is rewritten. That is where this record stops short of a verdict, because the row's notes
carry a cite only for the filter half -- "single static cloudfront etfs.json document; filtering
happens client-side in pandas (helpers.py:389)" -- and no cite at all for what symbol_normalization
does. So the label is charged as unproven in both directions: not split, and not trusted.

That leaves the row in the same shape as the contradiction closed in the registry recheck: its two
needs are both present capabilities while its flag reads expressible_today=false, and it is one of
the 3 surviving cover rows. The deciding reading was the cited upstream line, and it cannot be
taken here -- measured on disk, neither carrier holds it:

  ls .../site-packages/openbb_tmx*                                 -> no matches found

helpers.py:389, the row's other cite, is inside that same absent package. So the flag is left
exactly as the census has it and the row is marked unproven in both directions rather than
certified or split; cover stays at 3 with one row resting on an unreadable cite, which is stated
here instead of being averaged away.

7. what this split does and does not prove about the upstream side
--------------------------------------------------------------------------------
The four new entries are proven absent from repository bytes only: each anchor is a line in this
repo's engine, and each probe reports decls=0 because the field it names does not exist here. The
rows' upstream claims ride on the carrier the provider has. For the tmx pair that contributes the
+2, "rows are indices[query.symbol].constituents" is an assertion about openbb_tmx bytes that are
neither installed nor vendored -- the carrier census reads tmx as 24 rows, 23 oracle_missing and 1

while the source-side shape does not. An absent capability plus an unreadable source is a row that
cannot be closed by declaration either way: it is not evidence that TMX needs the parameterized
pointer, only that nothing in this repo can express one if it does.

9. the repair, and the re-derivation that keeps the refuted face checkable
--------------------------------------------------------------------------------

  * --check never writes. With --json it prints
    "READ-ONLY: <path> not written (generate mode writes; pass --round-id)" and leaves the bytes.
  * --round-id has no argparse default. Absent, the face opens with
    "NOTE: round label C75 is the tool default, not read from the tree", so a suggested label is
    never printed as if the tree reported it; DEFAULT_ROUND_ID moved C74 -> C75 to match the
    artifact it labels.
