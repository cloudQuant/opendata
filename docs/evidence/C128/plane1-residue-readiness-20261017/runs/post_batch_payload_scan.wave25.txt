--- what each zero here does NOT prove ---

1. `payload_scan_findings=0` says nothing about files outside the 23 roots. The whole-tree gate member
   (`make secret-check`, plus member 5's untracked-evidence census) is a different population and a
   different tool; it has not been re-run this wave.
2. Neither scanner reads the judge. A clean scan cannot make a row accepted, and a row's ACCEPT cannot
   make a scan clean.
3. gitleaks is regex-shaped: an actual credential in a form its rules do not match would still read 0.
   That is why arm B exists and why arm B's target is a file the scanner already covers.
4. Self-reference limit, stated plainly: the face line for take N is appended after take N ran, so
   take N did not scan its own face line. take N+1 scans it. The last line of this file is covered
   only by the next wave's scan, which is the same limitation every carrier of this shape has.
