--- what the columns mean ---

Every `raise` site in a provider package (and in `providers/_engine/`) whose first argument is a
SCREAMING_SNAKE literal is recorded, and bucketed by the method that holds it:

* `td` -- `transform_data`. The engine protocol hands it the decoded payload
  (`_engine/http_json.py:1462`), so a document tamper reaches a refusal here by construction.
* `ed` -- `extract_data`. Document-adjacent but ambiguous: `commodity_psd_report.py:104` (the
  PDF magic-byte check on the fetched body) sits in `extract_data` and landed this wave, while
  `weather_bulletin_download.py:112` sits in `extract_data` too and fires *before* any transport.
  A method name cannot separate those, so the two counts are printed apart and never merged.
* `other` -- every other method, class helper or module function, including a helper that
  `transform_data` calls. Unreachable by tampering a response body.

Codes raised through the `_fail("SUFFIX")` factories or the engine's
`f"{spec.error_prefix}_SHAPE_INVALID"` are resolved by suffix match, and a code that resolves only
in the engine is reported as `engine`, not as "no guard exists" -- that single reading is what
turns 28 declarative rows from false negatives into what they are, rows whose guard is real and
lives in shared code.

--- the three arms ---

* `A_landed_codes` takes the 266 accepted rows' own `expected.refusal_code` values out of the landed
  judge report (99 distinct codes, 24 providers) and resolves each one. `absent=0` is the pass
  condition, and it is the arm that found the engine shape. The same arm run four times read
  `unexplained=60`, then `absent=9`, then `absent=4`, then `absent=0`; the four lines are verbatim in
  the pre-fix-readings block at the end of this file. The split (136 td / 21 ed / 78 other / 28
  engine / 3 text_only) is the instrument's own coverage statement.
* `B_two_sided` requires the 4 accepted `government_us` rows to resolve into a document method and
  `models/weather_bulletin_download.py` to contribute zero `td` sites. Both halves are the same rule
  applied to a row the wave landed and the row the wave refused; if the module's strict count had
  been non-zero the arm would have gone red and the wave's exclusion would have needed re-arguing.
  Its `ed=0 other=0` is because those nine guards are `ValueError("NWS ...")` sentences, not
  code-shaped literals -- the screen only counts raises a counterfact could name.
* `C_planted_negative` resolves a code that exists nowhere and requires the counter to read
  `absent`. Without it, `absent=0` in arm A is an unfalsifiable zero.

--- the arithmetic that closes ---

`guard_face residual_units=13 residual_rows=84 residual_rows_no_package=2` -- 84 is the same residue
`readiness_census.py` prints from the other direction, and it decomposes per provider here against
the seam census's mechanism partition (24 tmx runner-surface, 46 engine-transport, 7 client-seam,
5 deribit other-module, 2 no-package). `strict_positive_providers=9 strict_zero_providers=2`: the
two strict zeros are `seeking_alpha` and `wsj`, whose 3 + 3 rows have no code-carrying raise site
anywhere in their package.

--- limits of this screen ---

1. `td=0` is not "unwitnessable": a refusal living in a helper called from `transform_data` lands in
   `other`, so the strict count is a floor. `screen=GUARD_PRESENT` says the provider has at least one
   document-reachable site; it does not say the residual row's own fetcher has one. That per-row
   reading is the author's job and is exactly the step §86.8 skipped.
2. Nothing here is a judge. It prints a screen and exits non-zero only when one of its own three
   control arms fails, so it can never be read as acceptance evidence for a row.
