--- why this instrument, in one line ---

Every phase receipt pins `before_sha256`/`after_sha256` for the files it read. When a wave edits a
shared file -- the runner, the fixture builder, another provider's witness module -- after some
receipts were produced, those receipts silently keep pinning bytes that no longer exist. Gate member 2
catches that eventually, several waves late, and the charge lands on whoever is standing there. This
gate asks the question inside the wave, before the commit.

--- the three arms, and what each one is against ---

* A is the claim: 228 slots in this wave's scope and 19382 tree-wide, every pinned digest equals the
  worktree bytes, `stale=0`, no missing path.
* B replaces one pin's *expectation* with a real digest taken from a different pinned file
  (`iter2_claims_probe_runner.py` standing in for `iter2_claims_fixtures.py`) and requires
  `stale == targeted_slots`: 20 of 20 in scope 1, 1330 of 1330 in scope 2, because that path is pinned
  by exactly one entry per receipt. Without B, `stale=0` would be unfalsifiable -- it is the same
  reading a `if pin.get(...) == ...` typo produces.
* C is the counter-proof for the *new* counter only. It builds one slot in memory whose path really
  exists on disk, whose `after_sha256` is that file's real digest, and whose `before_sha256` is 64
  zeros. Expected and obtained: `stale=0 before_ne_after=1`. A reads 0 in both scopes with C at 1, so
  the arm-A zero is a measurement of the receipts, not a dead wire. C never touches the disk.

--- the finding the third arm was added to make safe: the pin pair carries no mutation claim ---

Measured, not asserted: across all 19382 slots of all 1330 receipts, `before_sha256 == after_sha256`
in every one (`before_ne_after=0`, denominators 228 and 19382 printed beside it, per-kind breakdown
contract 2730 / fixture 2522 / probe 7290 / source 6840). The recorder writes the same digest into
both fields. Consequences for anyone reasoning from receipt pins:

* A pin is a *pointing* claim ("this file's bytes were these, when this phase ran"), not a diff claim
  ("this file changed from X to Y"). Reasoning of the second kind is unsupported by the artifact.
* Therefore the only live falsifiable content of a pin is `after_sha256 == worktree bytes`, which is
  arm A / arm B. The `before_sha256` field is currently information-free, and this probe keeps it
  counted so that stays visible instead of becoming folklore.
* This is a reading of the *current* tree. If a future producer starts writing differing pairs,
  `before_ne_after` becomes non-zero and is no longer evidence of degeneracy -- re-run, don't reuse.

into a counter, and the counter into an arm that can move. Lesson kept: an instrument's limits have
to be written from its printed lines, not from the ad-hoc code that answered the same question.

--- what this gate does NOT cover, stated so it is not mistaken for coverage ---

1. It does not verify that a mutation a receipt claims actually happened -- and per the finding above,
   the receipts claim none: 19382 of 19382 pin pairs are equal. Whether a counterfact's before/after
   pair really differs is that phase's own `expected==observed` face, not this one.
2. Equal-to-worktree is not equal-to-HEAD. This probe reads the worktree; `git grep` against HEAD is a
   different face and gate member 2 runs that one.
3. `stale=0` says nothing about rows the judge does not accept; scope 2 walks every receipt file on
   disk, including ones for rows still INCOMPLETE.
4. Arm C re-arms only the `before_ne_after` counter. Arm A itself has no second arm for "path missing
   from disk" as distinct from "path present, digest differs" -- both fold into `stale`, and `samples`
   is capped at 5 by design, so a large stale set prints 5 examples rather than a histogram.
