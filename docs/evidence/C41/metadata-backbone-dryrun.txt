读数（本 round 的结论，不外加任何未测到的东西）
================================================================================
1. --days 40 真的生效了：修正 _legs 之前同一命令返回 240 行（等于整张发布表），
   修正后返回 28 行，且 returned span 完全落在 [2026-08-18, 2026-09-26] 内（inside window = True）。
   原因：之前只调 extract_data，发布窗口原样返回；现在走 Fetcher.fetch 的
   validate -> extract -> normalize 全链路，日历的裁剪在 normalize 阶段（先推导后裁剪）。
2. prev_trade_date 是可用的 witness，不是空列：28/28 行都有值，邻居链自洽
   （rows[i].prev == rows[i-1].date 且 rows[i].next == rows[i+1].date 全为 True），
   且窗口首行 2026-08-18 的 prev = 2026-08-17 在窗口之外 —— 证明推导发生在裁剪之前，
   这正是 CalendarView._with_witness 需要的那一列。
3. next_trade_date 只有 1 行为 None，且在发布覆盖面的末行（2026-09-24）：
   与该适配器 docstring 的声明逐字一致（末行的后继上游不发布，因此不猜）。
4. 本腿只发布开市日（is_open all True，closed rows = 0，240 行全是开市日）。
   落地后 CalendarView 靠 coverage 区间把覆盖面内的周末/节假判为闭市：
   259 个工作日 - 19 个未发布工作日 = 240，读数自洽；19 条为国庆/元旦/春节/清明/劳动/端午，
   与 A 股休市安排同向（本 round 不引入第二个 vendor 去逐条对账，那是 C13 已做的面）。
5. 新发现（如实记录，不掩盖）：发布尾端落后。本地钟 2026-09-26（周六）读，对应北京
   2026-09-27 05:2x，覆盖面末行是 2026-09-24（周四），而彼时“最后一个已完成的交易日”
   应为 2026-09-25（周五）。也就是说适配器 docstring 里「ending at the last completed
   trading day」这句只在 C13 那次读数（2026-09-25 读到 2026-09-24）成立，不是一条规则。
   后果：warehouse_calendar 的 coverage 末行了 09-24，09-25/09-26 落在 coverage 之外，
   由 weekday tier 回答（周六闭市、周五开市），witness 面没有对应行可比 —— 不报错也不误判，
   但「最近 1~2 个交易日由落地行回答」这句话现在不成立，已回写到 docstring。
6. instrument 腿两页都通过 transform_data 的形状检查（空表 / thscode 重复 / 快照日期缺失），
   并按 symbol 升序返回；跨页 symbol 交集 = 0，所以 (symbol,) 单键 upsert 不会互相覆盖。
   a-share 5578 行里 list_date 为 null 的只有 8 行（C19 曾见整表全空 22/36 次），
   a-share-index 1431 行 0 null；status 两页都是全 active —— 与 C14/C19 的「目录只含当前在市标的」一致。
7. 落地面（列名/键/追溯列）就是 dwd_merge 的那一份：contract 列 + source/_merged_at/_diff_flag/_as_of，
   追溯列 null 计数 = 0，键 = (symbol,) 与 (exchange, date)，表名 dwd_instrument / dwd_trading_calendar。
8. 全程只读：engine=None，land 回调只做 len(frame)；没有任何 DDL / INSERT / UPSERT，
   连的是 fuyao 元数据端点的读请求。--write 与它需要的建表是运维决策，本 round 未执行（见 README）。
