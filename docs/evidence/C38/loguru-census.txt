  what a handler actually receives, per template:
    %s args on a loguru logger       -> 'Background download failed for execution %s: %s'

    args with no placeholder         -> 'no placeholder at all'

  这一格是整轮结论的支点，所以四个方向全部实测，不引任何文档说法：
    · loguru + %s → 参数丢掉，模板原样进日志（第一条读数）；
    · loguru + {} → 参数进入日志（本轮改后的形态）；
    · loguru + 无占位符 → 参数丢掉，且连模板线索都不留；
    · logging + %s → 正确；logging + {} → 消息根本没到 handler，
      异常被 logging 自己吞在 handleError 里、打到 stderr（上面最后三行读数）。
  两家的失败方向相反，但代价不对称：logging 失败是吵的（stderr 一条 TypeError + Message + Arguments），
  loguru 失败是静默的（消息照样发出去，只是参数没了）。这就是为什么 %s 写法能在库里活这么久没人发现。
  所以「看到 %s 就改」不成立 —— 得先判这个 logger 名字绑到哪一家，这就是 [1] 那个脚本存在的理由。
