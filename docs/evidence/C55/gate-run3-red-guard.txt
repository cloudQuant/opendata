## 1. 归因一：新的入口级模块进了选择器，reviewed 清单没跟上（两条红）

本轮新建的 `tests/test_data_query_http_warehouse.py`（23 例，`pytestmark = integration`）被
`-m "integration and not e2e"` 收进来了，而把这个集合称为「P0 域集成测试」的**评审清单**
`P0_INTEGRATION_MODULES` 里没有它 —— 于是同一个面被两台仪器量出了两种结果：

- `tests/test_p0_integration_surface.py::test_the_marked_set_is_the_reviewed_set`
- `tests/test_acceptance_probe_gate.py::TestC51ZeroDepCells::test_the_judge_and_the_guard_module_count_the_same_surface`
  （判据 `tool.integration_units_now()` ↔ 守卫模块的 `declared`，两边必须逐字相等）

处置：**评审后把这一条加进清单**。这份清单自己的注释写着「Adding one is a review step: it changes
what "the P0 domain integration tests" means」，所以这里就是一次真实的评审：新模块是 P0 域
（`stock_daily`/`stock_adjust`）走真 SQL 引擎的入口级面，属于这个分母；而 C55 重跑的干净环境留档
`docs/evidence/C55/clean-env-integration-run.txt` 里已经点名它 48 次 —— 加进清单不是
空话，判据 AC-16|07 的 `archive_blind` 面量的就是「留档有没有覆盖每一个在集合里的模块」。

没走的路，两条都不走：① 摘掉新模块的 `integration` 标记（等于把 23 条用例从 AC-16|07 的分母里拿掉，
为了红变绿而把判据要量的面改小）；② 把清单改成 `<=`（`test_the_marked_set_is_the_reviewed_set`
的判据是「分母不许意外漂移，两个方向都不许」，改窄比较就是放弃那个方向）。

## 2. 归因二：留档定位改名，守卫用例还按旧常量读（一条红）

本轮为了 AC-11|04 把「按轮次扫描留档」做成通用工具：`newest_round_archive(basename)`
（AC-11|04 用同一把尺子定位 `window-pruning-explain.txt`），AC-16|07 的留档常量随之从
`CLEAN_RUN_EVIDENCE`（一个固定路径）变成
`CLEAN_RUN_BASENAME`（一个文件名 + 目录名里的轮次标号），判据现在读的是**最新一轮**那一份，并要求
它正文声明的 `ARCHIVE_ROUND=` 与所在目录名相等（拷一份旧档到新目录会撞这条）。
守卫用例 `test_the_clean_environment_archive_the_judge_reads_is_shipped` 仍按旧名字读 ⇒
`AttributeError: module ... has no attribute 'CLEAN_RUN_EVIDENCE'`。

处置是让用例钉的对象跟着判据走：**读判据实际会读到的那一份**，钉它自己声明的轮次、
`CLEAN_SECTION`、`CLEAN_RUN_EXIT=0`、两个上游包 absent、选择器至少出现 3 次 —— 一条钉子都没少，
只是不再钉「历史上那次是 C51」。`docs/evidence/C51/clean-env-integration-run.txt` 一字未动。

没走的路：把 `newest_round_archive` 退回固定路径（那是为了让一条用例绿而把判据读窄），
以及在用例里 `getattr(tool, "CLEAN_RUN_EVIDENCE", ...)` 兜底（把 AttributeError 变成静默跳过）。
