## 这一轮在证成什么

设计 §9.3 把增量窗口钉在交易日 **17:30** 起跑。这条时间选择有个真实风险：
调度**成功执行、却拿不到当日 K**（上游还没写当日数据），从而水位前进、数据却没有落地。
AC-13 的第 8 条判据「调度时间业务校准完成（真机实测调窗，避免『成功执行但没拿到当日数』）」
就是为了不让 17:30 变成一个凭感觉写下的数字。B3 是这条判据的第一份、也是唯一一份直接读数。

## 这份读数**不**证明什么

1. **一个点不是一条曲线。** 它能证伪「15:00 就有当日 K」，不能证实「17:30 一定有」。
   现在能夹出的区间只有「2026-09-24 15:01 未返回 → 同日晚间某时刻已返回」：
   B4 的取数日志 `scene1_real_run.log` 与 `real_run_ths_incremental.log` **没有时钟戳**，
   带 `2026-09-24 18:02:02` 的是 `scheduler_startup.log`，而那是开机注册作业的读数、
   不是取数时刻。把 18:02 当成「当日 K 落地的上界」是一次跳步，C43 点名它。
2. **通道只对 ths（fuyao）成立。** 文中写明此前因 eastmoney 拒连而挂起、本日改用 ths；
   所以对 em / sina / akshare 通道的「当日 K 何时可取」没有任何结论，多通道校准未做。
3. **它校准的是上游的写入时点，不是本仓库的行为。** 水位前进而数据没落地这条风险，
   在跑批侧是否真会发生，属于 AC-13 第 3、4 条（断点续拉 / 水位以 ods 为准）的面，不由 B3 证成。
4. **真机读数不进门禁。** `make gate` 跑 `-m "not e2e"`，B3 是一次人工探测，
   没有任何断言在每次门禁里复现它；它是「当时那台机器 + 那把 key + 那个上游状态」的观测。
