## Face B — does coverage tracing reach the test's own subprocess? (it does; my earlier claim refuted)

Instrument: `python3.11 docs/evidence/C76/worker-cov-env-probe.py`, raw output archived as
`worker-cov-env-face.txt`. It reads `COV*` at three levels — controller, xdist worker, and the
`python -c` grandchild spawned from inside a test — under three arms (serial with `--cov`, serial
without, `-n 2` with `--cov`).

Reading: with `--cov` active, `COV_CORE_CONFIG`, `COV_CORE_DATAFILE` and `COV_CORE_SOURCE` are present
in the controller, in both `gw0`/`gw1` workers, *and* in the grandchild's environment; without `--cov`
all three are absent. `site-packages/pytest-cov.pth` gates `pytest_cov.embed.init()` on exactly
`'COV_CORE_SOURCE' in os.environ`, so the grandchild starts a traced interpreter (`pytest_cov/embed.py:50-53`
builds `coverage.Coverage(..., data_suffix=True)`). Not established here: where those suffixed data
files land in a gate run — the harness's grandchildren imported nothing from `source`, so no data file
appeared in either the scratch dir or the repo root, and the claim stays at "the tracing is started".

Cost, from the same harness (parent-side spawn → the child's first executed line, 2 children per arm):

- untraced: `[0.04, 0.04]` s
- traced, serial controller: `[0.115, 0.121]` s
- traced, xdist worker: `[0.131, 0.129]` s

so tracing adds ~0.08-0.09 s to the worker's boot *before* its own clock starts. The harness passes
`--cov-config` pointing at a scratch config, while member 12 uses the repo's `pyproject.toml`
(`branch = true`, whole `opendata` source set), so those boot numbers are a lower bound.

Explicit refutation, kept in the record: an earlier probe of mine concluded "an xdist worker under
`-n 2 --cov` carries no `COV_*` variable at all", and a sentence saying so had been written into
`tests/test_minute_archive.py`. That was an instrument artifact — the surviving face from that probe
is a single stub line (`40513 (none)`), one pid, read from a harness whose output was never captured.
The corrected sentence is in the committed comment; the wrong claim is quoted here so a future reader
can see which way the evidence moved.

## Face C — the same test traced vs untraced, one box, back to back

Instrument: `sh docs/evidence/C76/lock-test-tracing-pair.sh`, raw output archived as
`lock-test-tracing-pair-face.txt`. Arm `on` keeps `pytest.ini`'s addopts (so member 12's exact flag
set); arm `off` drops addopts.

- wall: `1 passed in 7.39s` traced vs `1 passed in 2.25s` untraced
- the test's own call: `2.53s` traced vs `2.02s` untraced (two workers, so ~0.25 s each — consistent
  with Face B's +0.08 s traced boot plus traced imports)
- worker stage markers (the worker's own clock, from its first line): `purge 1.00s / writer 1.02s`
  traced vs `purge 0.87s / writer 0.88s` untraced
- the remaining `7.39 - 2.53 = 4.86` s is pytest-cov's own work (`--cov-report=term-missing` over
  26,278 statements + `htmlcov`), not the worker. It is in the wall but not in the budget.

Limitation of this instrument, stated so it is not over-read: the worker *rewrites* its stage file as
it goes, so the archived face carries only the last stage. Intermediate stamps are not recoverable
after the fact.

## Face D — the worker under member-12-like peer contention

Instrument: `python3.11 docs/evidence/C76/worker-startup-contention-probe.py 3`, raw output archived
as `proxy-run-face.txt`. It starts 7 peer `pytest` processes (each with the repo's traced addopts) and
then runs the two-arm lock test plus the stall counterfact in the 8th slot.

- `run 0: 2 passed in 17.12s`, `run 1: 2 passed in 13.54s`, `run 2: 2 passed in 12.78s`
- worker's own `finished-work` clock: `purge 1.62 / writer 1.49`, `purge 1.52 / writer 1.59`,
  `purge 1.46 / writer 1.47` → 1.46-1.62 s across six repeats, against 0.87-1.02 s alone (Face C)
- boot probe (harness-side, therefore *untraced* — the harness is a plain `python3.11` process, not a
  pytest one): `0.04-0.05s`

Peer contention multiplies the worker's own work ~1.6-1.7x. That is the whole measured effect. It
does not come near 120 s, which is why the budget is not derived from these numbers as a "typical +
margin" but as twice the one observed instance.

## Face E — a pure-CPU load proxy, and what it cannot reach

Instrument: `python3.11 docs/evidence/C76/saturation-probe.py`, raw output archived as
`saturation-probe-face.txt`. Arms: `n=4` cold imports of `opendata.data.minute_archive` with the
worker's import set, and `n=30` samples of an `asyncio` sleep overshoot, at 0 and 12 busy-spin
processes.

- cold import: load 0 `median=1.7940 max=2.0059` → load 12 `median=9.6654 max=10.0398`
  (paired run; a 5.4x multiplication of that one import)
- applied to a 1.5 s arm that lands near 8 s — an order of magnitude short of the 120 s instance
- `asyncio` sleep 0.3 s overshoot: `max=0.0510` s idle, `max=0.0285` s under load 12 (30 samples each;
  the idle arm was the worse of the two, so both are quoted). The sleep-0.07 s arms read
  `max=0.0012`/`0.0014` idle and `0.0048`/`0.0054` loaded.

The overshoot row is Face F's carrier for the warehouse deadline: the relation the test needs is
`each chunk (0.6 s) < deadline (1.0 s) < sum of chunks (1.2 s)`, i.e. 0.4 s of slack, which is ~8x the
worst measured overshoot.

## Face F — void measurements, kept so they are not re-cited as support

Two numbers from my earlier harnesses are **not** used by any constant, and are recorded so they do
not get re-mined later:

1. `coverage run -p -c CODE ...` is not a valid invocation (`coverage run` has no `-c` option; it
   errored with "no such option: -c"). A harness that printed elapsed values for those four arms
   therefore printed numbers for runs that never started. Void; the contention probe in Face D avoids
   the shape by invoking real pytest modules instead.
2. An earlier "load=0" pair reported 10.97 s spawn→marker and 13.4 s for the same arm, which is
   irreconcilable with Face D's 1.46-1.62 s child clock and Face C's 2.02 s untraced call. Cause
   unknown (the harness's load bookkeeping was not captured), so neither number is used anywhere.

What the budget enlargement does *not* do: mask a broken worker. Two counterfacts were added and both
fire in seconds, so the 240 s is not an untested licence —

- `test_a_dead_worker_is_reported_dead_not_as_a_lock_miss`: a worker that exits 3 is reported by exit
  status (`rc=3`, `boom`) in well under 20 s, never as a lock miss;
- `test_a_stalled_alive_worker_is_killed_and_reported_by_stage`: a worker given a 2 s budget that
  stalls after its `imported` stage is killed and reported with that stage and its own elapsed.
