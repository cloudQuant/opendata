===== D. 判据取舍：哪些断言可达、哪些是恒真，逐条量过 =====

-- D1 曾写「data 缺失时 query() 回退 emptyDataPage()」，跑出来是红的：拦截器 `res.data ?? res`
   在 data 为 null 时把整个信封交给调用方，`payload ?? fallback` 永远不会触发。
   该后端会不会真的发 success=True + data=null？量过：
$ sed -n '248,264p' opendata/api/data_query.py
    return APIResponse(
        success=True,
        message="success",
        data={
            "domain": domain,
            "asset_class": asset_class,
            "layer": layer,
            "source": source,
            "adjust": adjust,
            "columns": await _selected_columns(engine, table, query, domain),
            "rows": rows,
            "page": page,
            "page_size": page_size,
            "count": len(rows),
        },
    )

   → 域名查询要么返回完整分页 dict，要么抛 HTTPException（400/500/501），没有 success=True+data=null 这条路。
   处置：删掉该断言（它测的是拦截器性质，不是 query() 的性质），把这条性质挪到 utils/request.test.ts；
   同时登记 query() 里的 `?? emptyDataPage()` 为经真实传输不可达的兜底（emptyDataPage 本身仍被
   DataCatalogView 用作加载态，不是死码）。不为不可达分支加防御代码。

-- D2 success=false 是否可达（决定「200 但信封报失败」这条契约断言留不留）：
$ grep -rn 'success=False' opendata/api/*.py
opendata/api/settings.py:157:                success=False,
opendata/api/settings.py:187:                success=False,
opendata/api/settings.py:193:            success=False,
opendata/api/tasks.py:461:            success=False,
   → 可达（settings 三处、tasks 一处），契约断言保留。

-- D3 登记过的枪伤「res.data ?? res 会把自带 data 键的 payload 也解掉」在当前后端是否可达：
$ grep -rn '"data":' opendata/api/*.py
opendata/api/websocket.py:93:            "data": {
opendata/api/websocket.py:148:      "data": {
   → 只有 websocket.py 的推送帧自带 data 键，而 WS 不走 axios；REST 侧无一处。
     故它是结构性风险（新增端点时会被踩到），不是当前断链，本轮只登记不改拦截器。

-- D4 无信封端点（SettingsView 症状的来源）实测：opendata/api/settings.py 的 /settings/database
   直接返回模型对象，因此 `res.data ?? res` 走的是「整包透传」分支；
   SettingsView 原先的 `mainRes.data || mainRes` 是对同一件事的第二次猜测，已删。
