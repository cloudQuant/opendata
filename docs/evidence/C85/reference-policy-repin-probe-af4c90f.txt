  brand-carrying added line classified against the load-shape regex. arm5 is the arm that bites;
  arm6 is the arm that must stay silent, otherwise the loosening is a hole rather than a
  measurement change.

The face this run's first draft published wrong, and its correction

  The reason string read "变动行 增260 删0" while git reported the same drift as
  +401/-0. changed_lines() counts a text-deduplicated population: an added line
  whose exact text already occurred anywhere in the pinned bytes counts as zero. So the
  401 git-added lines collapse to 260 here -- the other 141 are lines identical to one already
  in the file (closing braces, blank lines, repeated dict rows). The number was never a diff
  count, but the label said 变动行, and a reader holding git numstat would have called it false.
  The same ambiguity sits in the 17 clauses the earlier C85 pass wrote: for the
  5e335ab -> 4b8df39 drift of this same file they published "变动行 增1595 删11" where git
  says +2068/-11. Those clauses are left exactly as written -- each is a measurement
  of a real population, and rewriting a record to make it read better is not on the table; the
  retained wrong number is what tells a future reader the label was ambiguous. The instrument now
  prints both counts in one sentence, read back verbatim from the clause above ("
 diff 口径（difflib autojunk=False，本轮与 git numstat 同形）增401 删0，按文本去重口径 增260 删0，两口径差 141 条（新增行与 pin 里的既有行同文，去重口径不计）
  "), which is what disambiguates the earlier ones retroactively. No gate rides on these
  counts: the multiset and load_shape_lines total every occurrence over the whole file, so a
  duplicated brand-carrying load could not hide in the deduplicated population.
