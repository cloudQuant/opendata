## 1. 背景与目标

### 1.1 背景

opendata 是新创建的数据中台项目，以 `akshare_web` 完整拷贝为起点（FastAPI + Vue3 + MySQL 双库 + APScheduler + 执行状态 WS），要为 backtrader、ai-for-investor、bt_api_py 等项目提供统一数据支持。

两个直接动因：

1. **数据获取能力要内化**：bt_api_py 迭代09 已完成"源码级整合 akshare + OpenBB 架构自研 + 同花顺客户端"的完整规划，但代码未实施。经决策 D1，该规划整体迁移到 opendata 落地，opendata 成为数据获取层的**唯一实施地**，避免两套重叠建设。
2. **数据要资产化**：当前拷贝仅有 1 个数据脚本落地、无 ods 规范、无多源校对、无数据订阅接口。数据中台要求把各数据源接入的数据按数仓规范落 MySQL，并提供查询与订阅服务。

三个数据源能力，形态与许可各不相同：

| 来源 | 形态 | 规模（实测） | 许可证 | 本项目可采取的动作 |
|------|------|------|--------|------------------|
| **akshare** | HTTP 爬取各站点 | **394 个 `.py` / 98,396 行 / 39 个子目录**（本地基线仓库为 406 文件 / 105,018 行） | **MIT** | **按需源码级搬运**（保留版权声明） |
| **OpenBB** | openbb_platform：core + 32 个 provider | 大 | **AGPL-3.0** | **仅借鉴架构，自研实现**（复制源码会传染 AGPL） |
| **同花顺扶摇 API** | REST，`X-api-key` 认证，A股/期货/期权/基金 | 中 | 商业服务 | 自建 `opendata_fuyao` 客户端 |

> **实测口径说明**：本仓库内嵌副本为 394 文件 / 98,396 行，与本地基线仓库 `/Users/yunjinqi/Documents/new_projects/akshare`（406 文件 / 105,018 行）存在差异（缺 18 个文件、多 6 个文件）。搬运基线以 D9 决策冻结为准。

### 1.2 目标

1. **品牌与合规改造**：项目全链路改名 opendata；许可证 MIT → BSL 1.1；建立数据源权利登记与免责声明。
2. **数据获取层内化**：`opendata_http`（akshare 按需搬运）+ `opendata_fuyao`（同花顺客户端）+ `opendata_providers`（OpenBB 风格自研）+ 统一数据契约与源路由；整合完成后运行时零 akshare / openbb 外部包依赖。
3. **数仓分层落库**：数据域按 `ods_`（一源一表，源原始列保真）落地 MySQL 数据仓库；同域多源经契约模型归一化后交叉校对；`dwd_` 合并层供查询。
4. **跑批与调度体系**：数据域 pipeline（取数 → ods 落库 → 校对 → dwd 合并 → 推送）纳入定时任务，支持断点续拉与失败重入。
5. **API 服务化**：REST 查询（含复权口径）+ WebSocket 订阅增量 + **最小 Python 客户端**，所有落库数据均有对应接口。
6. **消费方打通**：至少一个真实消费方（backtrader_web）经 API 完成回测数据准备（迭代 1A 末启动、1B 内完成）。

### 1.3 非目标

沿用 `初始需求.md` §6：不复制 OpenBB 源码；不做实时行情接入/转发；不做交易能力；**不支持多 worker 部署**（D8）；**不搬运与金融无关的 akshare 子模块**（D9）；不承诺冷门子模块与上游 pending 端点可用性；不发 PyPI；不做 dws/ads 分层。

## 3. 功能需求

### FR-1 品牌、许可与合规改造（WB-0）

- pyproject 项目名 `akshare` → `opendata`，版本重置为 `0.1.0`；Python 包 `app/` → `opendata/`。
- 运行时品牌统一：`app_name`、`.env.example` / `.env.production`、前端 title、nginx、docker-compose、systemd service、Makefile。
- **双库改名四处收敛**：`app/core/config.py` 默认值、`.env.example`、`docker-compose.yml`（含 `container_name`/卷名/`WAREHOUSE_DATABASE` 默认值）、`init.sql`，统一为 `opendata` / `opendata_data`。
- **改名范围补全**：容器名（`akshare_mysql`/`akshare_warehouse`/`akshare_redis`/`akshare_backend`/`akshare_frontend`/`akshare_certbot`）、`akshare_user`、根目录文档（`README.md`/`ARCHITECTURE.md`/`DEPLOYMENT.md`/`DEVELOPER_GUIDE.md`/`API.md`/`QUICKSTART.md`/`CODE_QUALITY.md`）、`Makefile` 与 `.pre-commit-config.yaml` 中的路径。
- **凭证与敏感文件隔离**：`.gitignore` 改为 `.env*` + `!.env.example`；排除 `.idea/`、`LICENSE copy`、`.DS_Store`；pre-commit 与 CI 增加 secret 扫描；首次完整提交前执行 dry-run 审计。
- 许可证替换为 **BSL 1.1**（Licensor / Additional Use Grant / Change Date / Change License 四要素齐备）。
- 建立 `THIRD_PARTY_NOTICES.md`：akshare MIT 版权声明、来源仓库与 commit。
- **数据权利合规（D11）**：建立数据源权利登记表；核查同花顺扶摇 API 条款是否允许落库后再分发；README/LICENSE 增补数据免责声明。
- 清理拷贝残留（`LICENSE copy`、`".gitignore copy"`、空 `.py`、`akshare_web.pid` 等）；git 首次完整提交；CI 基线（仓库当前无 CI，需从零搭建）。

### FR-2 统一数据契约（`opendata/data/`，自研核心）

- 定义与数据源无关的**标准化数据模型**：
  - 行情类：`Bar`、`Quote`
  - **复权类：`AdjustFactor`（复权因子）、`CorporateAction`（除权除息事件）**——`Bar` **只存不复权 OHLC**（D10）
  - 财务类：`FinancialStatement`、`FinancialIndicator`（含**报告期 / 公告日 / 重述版本**三个时间维度）
  - 指数类：`IndexConstituent`
  - **元数据类：`Instrument`（标的元数据，含 `list_date`/`delist_date`/`board`/`status`）、`TradingCalendar`（交易日历）**——两者为一等公民，支撑全市场回补与增量窗口计算
  - 其他：`MacroSeries`、`FundNav`、`FundHolding`、`OptionContract`、`OptionQuote`、`FuturesFundamentals`
- 定义**数据源协议**（三段式）：查询参数（QueryParams）→ 抓取器（Fetcher：validate → fetch_raw → **normalize** → 标准化模型）→ 标准化输出。
- 定义**能力声明**：每个数据源声明 `Capability(asset_class, domain, period, market, source, verified, notes)`——字段名全局统一（不再出现 `asset`/`asset_class` 混用）。
- **domain 注册表**：维护唯一 `domains.yaml`，表名、REST 路径、WS 协议、前端展示均由它派生。
- 模型可序列化为 `pandas.DataFrame` 与 `pydantic` 两种形态。
- **契约同时是 dwd 与 API 的 schema 上游**（ods 逐源保真，见 FR-11）。

### FR-3 provider 注册表与源路由

- 各数据源（opendata_http / opendata_fuyao / opendata_providers.*）注册进统一注册表，声明能力、**权威度**与 **`verified` 状态**。
- 路由规则：显式指定源时精确路由；`source="auto"` 时按"权威度 + 可用性"选择并降级；**`verified=false` 的能力不参与 auto 路由**。
- 未实现/上游 pending 的能力可先注册并标注 `notes="on-demand"` / `notes="upstream-pending"`，路由自动跳过。
- 对 API 层暴露统一查询入口（REST/WS 内部调用同一路由层）。

### FR-4 `opendata_http`（akshare 按需搬运）

- **搬运范围（D9）**：本迭代搬运 P0/P1 数据域涉及的子模块（stock、stock_feature、stock_fundamental、futures、futures_derivative、index、fund、option、bond、economic、utils 等）；**与金融数据无关的子模块（movie/news/nlp/air/fortune/cost/article/tool）移出本迭代**，进"按需接入清单"。
- **搬运基线（D9）**：以 `/Users/yunjinqi/Documents/new_projects/akshare` 的 commit 为基线，写入 `upstream.lock`；**冻结 manifest**（文件清单 + sha256 + 资源清单 + 子模块计数）。
- 根目录内嵌的 `akshare/` 副本改造为 `opendata_http` 包：包内导入改写为包内路径；运行时不要求安装 akshare；**运行时包中不再出现 `import akshare`**（含字符串形式的 `akshare.data` 引用）。
- **请求层渐进收口**：新建 `opendata/data/http_client.py` 供新代码使用；搬运代码的既有直连调用**保持原样**并逐条登记为债务，收口率作为棘轮指标只降不升。
- 公开函数沿用 akshare 原名、去掉 `akshare` 前缀（调用形态 `opendata_http.stock_zh_a_hist(...)`）。
- **内置资源处置**：实测资源为 `movie/jm.js`、`air/crypto.js`、`air/outcrypto.js`、`stock_feature/ths.js`、`file_fold/calendar.json`；`akshare/datasets.py` 引用的 `akshare.data` 包**不存在**（该函数当前已断链，被 20 个模块引用）——搬运时需一并修复或明确标注为不可用。
- 版权合规：每文件头保留 MIT 版权声明 + 来源标注；`THIRD_PARTY_NOTICES.md` 记录来源仓库与 commit；**上游硬编码凭证（`stock/cons.py` 的 token）在搬运前处置**。

### FR-5 搬运工具链（codemod）

- 半自动搬运工具，覆盖目录映射、导入重写、版权头注入、静态检查、差异报告；幂等、可重跑、可按子模块/文件粒度执行。
- **manifest 生成**：产出 `opendata_http/manifest.json`（文件清单 + sha256 + 资源清单 + 计数），供 AC-5 逐项校验。
- **字符串常量改写**：识别并改写 `"akshare.data"` 等字符串形式的包引用。
- 搬运差异报告：每个文件记录来源、行数、改写次数、人工待办清单。

### FR-6 `opendata_fuyao`（同花顺扶摇 API）

- 客户端能力：`X-api-key` 认证、统一响应信封解析（`code/message/request_id/data`）、错误码映射（0/1001–1004/2001/2003/3001–3004/4001/5001–5003）、429 与 code=4001 限流退避、超时重试、`request_id` 留痕。
- **错误业务文案表**：每条错误码映射一句中文业务文案 + 一条处置建议（如 4001 →"同花顺请求过于频繁，系统将自动退避重试，无需处理"），与错误码映射同源维护。
- 端点覆盖（以官方文档分组为准）：基础（标的检索/列表/交易日历）、A 股（行情、market-dumps、除复权事件流、财务报表与指标、估值、竞价、指数成分、资金、高频、特色）、期货、期权、基金。
- 认证与端点配置走 `.env` / 配置文件（不硬编码 Key）；Key 缺失时路由自动跳过该源并**发出醒目告警**（而非静默降级）。
- 数据映射到 FR-2 统一模型；`source="ths"` 可被路由。

### FR-7 `opendata_providers`（OpenBB 风格 provider 自研）

- 采用等价但自研的接口范式：`provider 接口类 + QueryParams + Fetcher + 标准化模型 + 插件注册`。
- 提供上游对照表（OpenBB 接口名 ↔ 本项目接口名），只描述契约不含实现。
- **分批原则（D9 修订）**：**按消费场景分批**，不按"清单数量"分批——每个 provider 需标注"消费场景 + 请求方"，标不出场景的移出本迭代，进按需接入清单。
- 依赖策略：各 provider 的第三方 SDK 作为可选依赖声明，不安装不影响其它 provider。
- 合规：**零 OpenBB 源码**；接口命名参考属事实性信息，实现全部自研并留审查记录。

### FR-8 上游同步机制

- 记录上游基线：akshare 仓库 URL + 搬运时 commit SHA + 每文件哈希，落地 `upstream.lock`（随库入库）。
- 同步工具：拉取上游新 commit，产出"新增/修改/删除文件"清单与关键函数签名 diff 摘要。
- **fork 维护预算**：每迭代预留 10~15% 人力用于上游同步与失效修复（写入实施计划）。
- **失效即弃策略**：连续 N 次健康检查失败的能力标记 deprecated、移出路由、不承诺修复。
- 同花顺侧：记录文档版本/抓取日期，端点变更时更新映射表。

### FR-9 请求治理（跨源统一）

- 统一超时、重试（指数退避）、并发上限、限流退避（429 与频率码）、失败分类（网络/限流/参数/数据未就绪/上游不可用）。
- 全局速率配置（按源），避免对同一站点高频请求。
- 失败可诊断：记录源、端点、参数摘要、`request_id`（若有）、耗时。
- **接口健康巡检**：P0 域接口每日自动巡检，失败累计触发告警。

### FR-10 缓存与增量

- **缓存只存原始响应**（不缓存标准化/复权结果）；缓存键含 `source + endpoint + 规范化参数 + adjust_basis + as_of + schema_version`。
- **水位真相源**：fetch 前的增量判断**以 ods 已有区间为唯一水位来源**（`SELECT MAX(trade_date)` / 区间 diff）；文件缓存仅用于 market-dumps 等大文件下载暂存与解析重入，**不承担水位职能**。
- 断点续拉：按标的分批拉取时记录进度，中断后可续（大任务如全市场 10 年日线）。
- 缓存可关闭、可清理、可指定路径；缓存内容不写进版本库。

### FR-11 ods 落库体系（一源一表）

- 命名规范：`ods_<domain>_<source>`（如 `ods_stock_daily_akshare`、`ods_stock_daily_ths`），位于 `opendata_data` 数据仓库库。
- **列结构（v2.0 澄清）**：**数据源原始列**（保持源命名与类型，不做语义清洗）+ 固定元数据列（`_source`、`_fetched_at`、`_batch_id`）。**ods 表结构由各源字段清单决定，逐源不同**。
- **DDL 归属**：数据仓库 DDL 由**独立 alembic 环境**管理（独立 version 表），应用启动只校验版本不建表；启动时 ensure-table 仅在 development 且显式开关下可用。
- 写入：批量 key 级 upsert（`ON DUPLICATE KEY UPDATE`），**幂等语义为"同一业务 key 更新"而非"同一内容去重"**；由通用化 `ods_writer` 承担（禁用 ORM 逐对象写入；大批量走 staging 表 + `INSERT...SELECT`）。
- **大表分区**：日线类大表按 `trade_date` 做 `RANGE COLUMNS` 年分区 + `MAXVALUE` 兜底分区；配套**分区自动维护任务**（每日检查并按需 `REORGANIZE PARTITION`）。约束：分区表所有唯一键必须包含分区键。
- **旧存量表转移**：验收阶段评估旧表与新 ods 表覆盖度，有增量价值则迁移 upsert（冲突以新抓为准），验证后 DROP。
- **schema 演进**：源端新增列默认忽略并记录；加列走显式迁移，不自动 ALTER。

### FR-12 多源交叉校对与差异报告

- **比对路径（v2.0 修订）**：**经契约模型归一化后比对**——`ods(源A) → field_mapping → 契约模型` 与 `ods(源B) → field_mapping → 契约模型`，按业务 key 逐字段比对。
- **口径映射表**：每个数据域显式声明字段映射、单位换算（手→股 ×100 等）、复权口径、key 规范化（`600519` ↔ `600519.SH`）、停牌日语义、差异率分母口径（建议取双方 key 并集）。
- 差异报告表 `dq_diff_report`（**落数据仓库库**）：记录数据域、源对、key、字段、两源取值、偏差度量、判定；**默认只存聚合统计 + 抽样明细**（阈值可配），全量明细走导出文件。
- 容忍度可配置（浮点相对误差阈值）。
- **告警治理**：已知差异模式白名单（按 domain+field 登记容忍项）、按 diff fingerprint 去重（连续相同差异不重复告警）、告警分级（新增差异率突增才升级）。
- 告警通道：SMTP 邮件 + WS `data.diff_alert` 事件。

### FR-13 dwd 合并层

- 命名规范：`dwd_<domain>`，位于 `opendata_data` 库；列结构 = **契约标准化模型字段** + 留痕列（`source`、`_merged_at`、`_diff_flag`）。
- 合并规则：权威源优先 + 降级源按权威度次序填补；数值字段差异不改变取值（仍取权威源），仅置 `_diff_flag=1`。
- **复权口径整段同源（D10）**：同一查询窗口内的复权因子不得混源。
- **修订传播（v2.0 新增）**：合并单元 = **增量窗口 ∪ 受影响 key 集合**（ods upsert 返回的受影响主键），确保被修正的旧 key 能传播到 dwd；另设周期性全量重建作为一致性收敛手段。
- **单源域恒启用**：单源数据域的 dwd 以直通模式生成（VIEW 或薄表），保证 `layer=dwd` 契约统一、WS 推送时机统一。
- 重算幂等；查询 API 默认查 dwd 层。

### FR-14 跑批与调度体系

- 沿用 APScheduler + `scheduled_tasks` 表，新增**数据域 pipeline 编排**：fetch → ods 落库 → 校对 → dwd 合并 → WS 推送，作为一个调度单元。
- **部署拓扑（D8）**：本期**单进程合一**（API + scheduler + WS 同进程，`WORKERS=1`），调度归属由显式配置 `ENABLE_SCHEDULER` 控制；生产模式下未显式配置则启动即失败。多 worker 列为非目标。
- 进度持久化（断点续拉状态落表），任务重启后可续。
- 失败重试、单标的失败不阻断全局、**失败清单一键重试**（前端按钮，非仅导出）。
- **新鲜度监控**：每日收盘后 N 小时检查各域 dwd 是否含最近交易日数据，缺失即告警（优先于差异告警）。
- **告警矩阵**：pipeline 失败、连续失败、分区缺失、磁盘水位、权威源 Key 未配置/配额异常。
- 跑批模板内置 P0 数据域；前端任务页面可配置（含任务向导）。

### FR-15 REST 查询 API

- 按数据域的查询路由（如 `/api/v1/data/stock/daily`），参数：
  - 标的、日期区间、`source`（auto|akshare|ths|…）、`layer`（dwd|ods，默认 dwd）
  - **`adjust`（none|qfq|hfq，默认 none）——服务端统一计算复权序列（D10）**
  - 财务域专有：`period` / `report_date` / 重述取舍
  - 分页、字段过滤、导出 CSV
- **参数安全**：`fields` 必须对该表实际 schema 做白名单校验；`layer`/`source` 使用枚举；`symbols` 走绑定参数；导出时对 CSV 公式注入前缀（`=`/`+`/`-`/`@`）做转义。
- **默认时间窗保护**：不带日期区间的查询强制默认窗口（避免全分区扫描）。
- 通用表查询（现有 `/tables` 能力保留并适配新分层命名与无 `id` 列的表）。
- 响应 schema 与 FR-2 标准化模型一致；OpenAPI 文档齐全。

### FR-16 WS 数据订阅

- 新增 `/ws/data/subscribe`：客户端订阅 `{domain, symbols?, source?, layer?, payload}`。
- **`payload=meta` 为一等公民（v2.0 修订）**：推送批次通知（domain/source/batch_id/window/rows），消费方按需经 REST 拉取；`payload=full` 保留但**标注实验性**（消费方自担分帧拼装成本），单帧上限 5000 行/2MB，超限分帧，极端总量（>10 万行/10MB）强制降级 meta。
- **批次水位与补发**：维护批次水位表，`subscribe` 支持 `since_batch_id` 补发 meta 事件，解决断线期间的事件丢失。
- **认证（v2.0 修订）**：**迭代 1B 前完成升级**——采用首帧认证（连接后 5s 内发 `{"action":"auth","token":...}`）或 `Sec-WebSocket-Protocol` 承载 token，不再使用 query token；nginx 对 `/ws/` 关闭查询串记录。
- 既有 `/ws/executions` 保留。

### FR-17 旧机制迁移

- `interface_loader`（反射扫描 akshare 全部公开函数入 `data_interfaces` 表）改为扫描 opendata 数据获取子包的**注册声明**；前端"数据接口"页与数据目录页合并设计（目录为默认视图，函数级明细下钻保留）。
- `data_acquisition.py` 中直接 `import akshare` 的执行路径改为经 provider 路由；**同时修正会话路由**（下载写入应走数据仓库会话）。
- `data_scripts` / `data_tables` 元数据表与前端页面适配新包名与 ods/dwd 分层。

### FR-18 数据质量对照（搬运保真）

- `opendata_http` 输出与 akshare 原实现做字段结构与取值对照（爬虫类接口以录制回放样本为准）。
- fuyao 与官方 Market Dumps Parquet 及文档示例对照。
- 自研 provider 与上游源官方输出逐字段对照。
- 产出对照报告（覆盖率、差异清单、容忍度说明）。
- **`verified` 标记**：未完成对照的能力在注册表中标注 `verified=false`，不参与 `source="auto"` 路由。

### FR-19 消费方对接与 API Key

- **消费方 API Key**（**v2.0 提前至迭代 1B，随 REST 落地**）：`api_keys` 表（哈希存储、挂靠用户、scopes 数据域白名单、基础限速、可吊销、**`expires_at` 过期机制**）；请求头认证与 JWT 共存；`/api/v1/keys` 管理接口。
- **最小 Python 客户端** `opendata_client/`（仓库内目录，git 依赖安装，不发 PyPI）：封装 REST 分页/认证/`adjust` 参数与 WS 订阅回调，提供 `client.stock_daily(symbols, start, end, adjust="qfq")` 级别的调用。
- 完成 backtrader_web 经 opendata API（使用 API Key + 客户端）取 A 股日线的真实对接。

### FR-20 数据目录与新鲜度（v2.0 新增）

- **数据目录接口与页面**：按数据域组织（不是按表名），展示覆盖标的数、时间范围、各源最近更新时间、**新鲜度（最新数据距今天数）**、质量标记（`_diff_flag` 汇总）。
- 机读版：`capabilities` + `freshness` 合并接口。
- **新鲜度告警**：见 FR-14；该能力在迭代 1A 即可交付（先于差异告警）。

### FR-21 错误文案与配置清单（v2.0 新增）

- **错误业务文案表**：错误码/失败分类 → 中文业务文案 + 处置建议，供前端提示、执行记录、WS 错误帧统一使用。
- **《配置项清单》文档**：键名 / 含义 / 改动影响 / 生效方式，覆盖凭证、QPS、超时、重试、缓存路径、兼容开关、告警收件人等。

## 4. 非功能需求（NFR）

### NFR-1 许可与合规（重点，一票否决）

- opendata 整体采用 **BSL 1.1**（Additional Use Grant：个人与非商业免费，机构/商用需授权；Change Date 后转 MIT）。
- **不得引入 AGPL 代码**（OpenBB 一律自研，隔离机制见设计 §1.3）。
- akshare 搬运保留 MIT 版权声明：每文件头 + 根 `THIRD_PARTY_NOTICES.md`（含来源 commit）。
- **混合许可边界可验证**：`registration.py` 等自研代码不得置于搬运包内；MIT 子树在无 BSL 模块时可独立运行。
- 整合完成后运行时不依赖 akshare / openbb 包，**CI 断言（分层 AST 口径：只扫运行时包 + 存量基线冻结 + 干净环境正向验证）**。
- **数据权利**：建立数据源权利登记表；README/LICENSE 含数据免责声明；商业授权定位为"软件授权"。
- 爬虫与商业 API 遵守各站点条款与限流要求。

### NFR-2 可维护性

- 搬运代码与自研代码**物理可分**；`upstream.lock` + manifest 支撑上游同步与审计。
- 单文件职责单一；公开函数有 docstring（Google 风格）；类型注解完整。
- 遵循现有分层（api/services/schemas/models/db/middleware），新增数据获取层独立成包不侵入服务层。

### NFR-3 可移植性

- Python ≥ 3.10；无平台特有依赖（`mini-racer` 系列需在 macOS/Linux 双平台验证安装）。
- 配置与凭证走 `.env`，不入库；脚本使用相对路径，可移植运行。

### NFR-4 性能与限流

- 批量拉取支持并发与分批，默认保守（不触发上游限流）。
- 缓存命中时不发网络请求；增量模式只请求缺失区间（水位以 ods 为准）。
- **全量回补写入性能**：单源日线 1,300 万行全量落库需有可复算的基准测试与耗时预算。
- 单标的失败不阻断全局任务，失败清单可一键重试。
- 全市场 10 年日线回补任务可在中断后续跑完成（不设硬性时长承诺，以进度持久化为准）。

### NFR-5 可观测性与告警

- 结构化日志：源、标的、区间、耗时、重试次数、失败原因。
- 任务级统计：成功/失败/跳过数量、产出摘要报告。
- 校对指标：各数据域差异率、告警次数入库可查。
- **新鲜度指标**：各域最新数据日期与滞后天数，每日检查并告警。
- **告警矩阵**：pipeline 失败 / 连续失败 / 分区缺失 / 磁盘水位 / **权威源 Key 未配置或配额异常**（避免权威源静默失效导致 dwd 全面降级而未察觉）。
- **错误文案**：面向业务的中文文案与处置建议。

### NFR-6 安全

- API 沿用 JWT 认证与限流；消费方 M2M 接入用 API Key（FR-19）。
- **WS 认证升级**：迭代 1B 前完成首帧认证或 `Sec-WebSocket-Protocol`，取消 query token。
- 同花顺 Key 等凭证仅经 `.env` 注入；**凭证不入版本库**（CI secret 扫描 + 首次提交前 dry-run 审计）。
- API Key：明文 ≥128 bit 随机（`secrets.token_urlsafe(32)`）、`sha256(pepper + key)` 存储、`hmac.compare_digest` 比较、支持过期与轮换；认证失败统一延迟防枚举。
- API 参数（`fields`/`layer`/`source`/`symbols`）白名单与枚举校验；导出防公式注入。

### NFR-7 工程质量（阻塞门槛）

> 详细规范见 `代码质量规范.md`，本节为约束摘要。

- **分层适用（v2.0 修订）**：A 层拆为 **A1 存量**（棘轮，只降不升）与 **A2 新增/触碰**（零容忍，"触碰即达标"）；B 层搬运代码仅 E/F 检查、保真优先；C/D 层各有豁免边界。
- **静态检查**：A2 代码 ruff 全规则集零违例、mypy 严格模式 0 errors、bandit 全量（例外行级精确带理由）。
- **测试基线（反空壳）**：禁止自指测试/单断言空壳/`inspect.getsource` 形式检查；按模块分档 T1~T5。
- **覆盖率**：A2 新代码 statement+branch ≥85%（契约/pipeline/fuyao ≥90%），阈值只升不降。
- **棘轮**：A1 存量与 B 层搬运债务快照只降不升，范围静默变更即失败。
- **公共 API**：**新增**公开 callable docstring 与参数注解覆盖率 100%。
- **门禁聚合 fail-closed**：`make gate` 逐项阻断（brand-check / zero-dep-check / **a2-check（A2 零容忍）** / quality-ratchet / public-api-quality / test-cov / 前端三项），子项失败不得被汇总掩盖。
- **证据文化**：质量"通过"声明必须附可复算命令与真实输出。

### NFR-8 容量与保留（v2.0 新增）

- 明确各数据域的容量测算（行数 × 单行字节 × 源数），标注 MySQL 适用边界。
- **分钟线不进 MySQL**（D13）：走 Parquet 文件 + 主库元数据索引。
- 保留策略：日线永久、分钟线 N 年（可配）、缓存 TTL、`dq_diff_report` 聚合数据保留 N 天。
- 选型触发阈值：单表 >5,000 万行 或 校对查询 P95 >10s → 启动存储演进评估。

### NFR-9 备份与恢复（v2.0 新增）

- 数据资产（ods/dwd）每日备份（mysqldump / xtrabackup）+ binlog，RPO ≤24h。
- **恢复演练**至少执行一次并纳入地基阶段 DoD——爬虫历史（尤其冷门区间）可能不可再生。
- 备份策略与恢复步骤写入运维文档。

## 5. 约束与假设

### 5.1 约束

1. **OpenBB 为 AGPL-3.0**：只能借鉴接口形态，禁止任何源码复制。自研判据：独立编写 + 对照表但无源码参照 + 代码审查留档。
2. **akshare 为 MIT**：可以搬运，但必须保留版权声明与来源 commit。
3. **akshare_web 既有业务能力不能断**：用户/认证/任务/执行记录/表查询等既有序列在重构中保持可用（渐进改造，不做大爆炸重写）。**注**：既有开发库数据可弃（项目尚未投产），业务连续性指代码能力而非历史数据。
4. **MySQL 双库架构保留**：主库（元数据）+ 数据仓库（数据），仅改名。
5. **同花顺为商业 API**：受限流与历史窗口上限；**数据再分发条款待确认（D11）**。
6. **部署形态**：单进程合一，不支持多 worker（D8）。
7. **git 仓库现状**：仅 1 个 commit、跟踪 2 个文件，地基阶段需完成首次完整提交建立基线。

### 5.2 假设

1. 部署环境可访问目标站点/API（国内站点可达、**海外源需要代理，代理可用性待确认**）。
2. 同花顺 API Key 已具备，可真实联调。
3. 消费方经 opendata API 取数，不直接 import opendata 内部包。
4. **MySQL 分级承载**：MySQL 承载日线及以下频度结构化数据（单源约 1,300 万行/10 年，双源 + dwd 约 3,900 万行，约 4.5 GB）；**分钟线走文件存储**（单源 10 年约 389 GB）。
5. **商业源 Key**：P1 商业源 Key 是否具备待确认，未具备的移出本迭代。
