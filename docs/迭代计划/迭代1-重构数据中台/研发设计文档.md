## 1. 设计目标与原则

### 1.1 目标

1. 把 akshare_web 拷贝改造为品牌统一（opendata）、许可清晰（BSL 1.1）的数据中台服务。
2. 建立数据获取层：统一契约 + provider 注册路由 + 三个数据源包，运行时零 akshare/openbb 依赖。
3. 建立数仓分层（ods 逐源保真 → 校对 → dwd 契约统一）与跑批调度体系。
4. 建立服务层：REST 查询（含复权口径）+ WS 订阅增量 + 最小 Python 客户端。
5. 既有 akshare_web 业务能力保持可用，渐进迁移。

### 1.2 设计原则

- **物理可分**：搬运代码（opendata_http）与自研代码分包放置，来源标注清晰；**自研代码不得置于搬运包内**。
- **schema 分层单源**（v2.0 修订）：**dwd 表结构与 API 响应结构由统一数据契约推导**（单源）；**ods 逐源保真**，其列结构由各源字段清单决定。
- **契约层职责**：提供 dwd schema + 每个源的 `field_mapping`（源字段 → 契约字段 + 单位换算 + 复权口径），该映射同时是校对与 dwd 合并的输入。
- **渐进改造**：不做大爆炸重写；旧机制按兼容路径迁移（§11）。
- **服务边界**：消费方只经 REST/WS API 取数，不 import opendata 内部包。
- **默认保守**：对外请求默认低并发、低频率，避免触发上游限流。

### 1.3 合规边界（许可隔离机制）★

**AGPL 隔离（防传染）**：

- OpenBB（AGPL-3.0）的任何源码不得进入本仓库——包括"改写变量名"式的近似复制。
- 允许：阅读其公开文档与接口命名（事实性信息），自研实现三段式范式。
- 自研判据：独立编写 + 接口对照表但无源码参照 + 代码审查留档。
- CI 防线：代码审查清单 + 提交说明要求声明"无 OpenBB 源码参照"。

**BSL 与 MIT 混合（防误解）**：

- 仓库整体 LICENSE 采用 BSL 1.1（Additional Use Grant：个人与非商业使用免费；机构与商用需书面授权；Change Date 后自动转 MIT）。
- `opendata_http` 内源自 akshare 的文件保留原 MIT 版权声明。**该部分代码他人仍可按 MIT 取用**——这是 MIT 的固有限制，无法通过整体 BSL 收回。
- **边界可验证（v2.0 修订）**：`registration.py` 等自研代码**移出** `opendata_http/`（放 `opendata/data/providers/` 或独立包）；为搬运文件提供**可选本地 requests 兜底**，使 MIT 子树在无 BSL 模块时仍可独立运行。
- 仓库根放 `LICENSE`(BSL) + `LICENSE-AKSHARE`(MIT 全文) + `THIRD_PARTY_NOTICES.md`；`opendata_http/` 内放 MIT 副本 + README 声明。
- **下游消费方合规须知**：明确"服务调用 / 代码复用 / 再分发"三种情形下的授权要求，避免消费方误判。

**数据权益与再分发（v2.0 新增）★**：

代码许可证 ≠ 数据权利。opendata 的模式是**集中爬取 → 落库 → 经 REST/WS 向多消费方再分发**，且 BSL 允许商业授权——这已构成数据分发/经营行为，与 akshare"工具中立、用户自担"的定位有本质区别。

- 建立**数据源权利登记表**：每个源一行（来源 / 条款链接 / 允许用途 / 是否允许再分发 / 复核日期 / 责任人）。
- 向同花顺索取**书面条款副本或授权**，明确"内部使用 / 衍生数据对外服务 / 再分发 / 商业变现"四项边界。
- README/LICENSE 增补数据免责声明：数据来源于第三方站点，本项目不主张数据权利，消费方自行承担数据使用合规责任。
- 商业授权话术定位为"**软件授权**"而非"数据销售"。

**运行时零上游依赖**：整合完成后 CI 断言运行时包无 `import akshare` / `import openbb`（分层 AST 口径，见 §5.6），且在未安装这两个包的环境中功能正常。

## 4. 统一数据契约（`opendata/data/`）

### 4.1 标准化数据模型

`opendata/data/models/`：

| 类别 | 模型 | 说明 |
|------|------|------|
| 行情 | `Bar`、`Quote` | **`Bar` 只存不复权 OHLC**（D10） |
| **复权** | `AdjustFactor`、`CorporateAction` | 复权因子与除权除息事件；复权序列由"原始价 × 因子"在查询/合并时合成 |
| 财务 | `FinancialStatement`、`FinancialIndicator` | 含**报告期 / 公告日 / 重述版本**三个时间维度 |
| 指数 | `IndexConstituent` | 支持按日期取历史快照 |
| **元数据** | **`Instrument`** | symbol / exchange / name / **list_date / delist_date** / board / status / currency |
| **日历** | **`TradingCalendar`** | exchange / date / is_open / prev_trade_date / next_trade_date |
| 其他 | `MacroSeries`、`FundNav`、`FundHolding`、`OptionContract`、`OptionQuote`、`FuturesFundamentals` | |

- **`Instrument` 与 `TradingCalendar` 是一等公民**：全市场回补的第 0 步是刷新 `Instrument` 全量（**含已退市标的**），fetch 步的 symbol 列表来自 `Instrument` 而非任何"当前快照"函数；增量窗口基于 `TradingCalendar` 的上一交易日计算。
- 每个模型提供 `to_frame()` 与 `from_frame()`。

### 4.2 三段式数据源协议

```
QueryParams（查询参数，含 source/market/symbol/range 等公共字段 + 域专有字段）
   → Fetcher（validate → fetch_raw → normalize → 标准化模型输出）
   → 标准化输出（DataFrame | list[Model]）
```

`normalize()` 是**口径映射的唯一归属地**：字段重命名、单位换算（手→股等）、复权口径、key 规范化（`600519` ↔ `600519.SH`）均在此完成，并被校对与 dwd 合并复用。

### 4.3 能力声明与注册表

- 每个 Fetcher 声明 `Capability(asset_class, domain, period, market, source, verified, notes)`——**字段名全局统一**。
- **domain 注册表** `opendata/data/domains.yaml`：唯一 domain 标识符（如 `stock_daily`），表名（`ods_stock_daily_<source>` / `dwd_stock_daily`）、REST 路径、WS 协议、前端展示均由它派生。
- 注册表 `ProviderRegistry`（进程内单例）：登记 Fetcher + 权威度 + 健康状态 + `verified`。
- 路由：`resolve(asset_class, domain, ..., source="auto")` → 按权威度排序候选 → 可用性探测 → 返回 Fetcher；**`verified=false` 与 `notes="on-demand"` / `"upstream-pending"` 的能力不参与 auto 路由**；显式 source 直接路由，失败时报错不降级。

### 4.4 权威度基线（国内域）

| 数据域 | 权威源 | 次选 |
|--------|--------|------|
| A 股日线/复权/财务/指数成分 | ths（同花顺） | akshare |
| 期货日线/基本面 | ths | akshare |
| **标的元数据 / 交易日历** | **ths（`/api/meta/*`）** | akshare |
| 宏观/海外 | 各 provider 声明 | akshare 对应域 |

**权威度复审机制**：当 `dq_diff_report` 显示权威源在某域持续高差异率时，触发人工复审或自动降权（见 §16 观察项）。

### 4.5 与落库/服务的关系

- `opendata/pipeline/` 依 **domain 注册表 + 契约模型**生成 dwd 表结构；ods 表结构由各源字段清单生成。
- REST/WS 响应模型 = 标准化模型（dwd 行直接映射）；`adjust` 参数在服务端基于 `Bar` + `AdjustFactor` 合成。

### 5.2 搬运改造规则

**实测 akshare 内部形态（决定搬运成本）**：

| 事实 | 数量 | 对搬运的意义 |
|------|------|-------------|
| `from/import akshare...` 绝对导入 | **553 行** | 机械前缀替换 |
| `requests.get/post` 直连调用 | **1,270 处**（301 文件） | **不做全量收口**（见规则 3） |
| 集中式 `akshare/request.py` | 117 行 / 2 函数 / 仅 4 文件引用 | 集中度低，收口收益有限 |
| `mini_racer` 使用文件 | 40 | 安全审计关注点 |
| 硬编码凭证 | `stock/cons.py:8` | 搬运前处置 |

**改写规则（codemod 逐条落实）**：

1. `from akshare.X import Y` → `from opendata_http.X import Y`；`import akshare.X` → `import opendata_http.X`。
2. 顶层 `akshare/__init__.py` → `opendata_http/__init__.py`，保持同名导出集合。
3. **请求层渐进收口（v2.0 修订）**：新建 `opendata/data/http_client.py` 供**新代码**使用；`opendata_http/` 内提供与 `requests` 同形的薄适配层；**搬运代码的既有直连调用保持原样**，逐条登记为债务，收口率作为棘轮指标只降不升。
   > 原规则 3 要求"各文件内 requests 直连全部收口"与本文件规则 7"不做顺手重构"直接冲突——收口 1,270 处会改写绝大部分搬运文件，使 `upstream.lock` 的逐文件哈希失效、diff 同步能力归零。故降级为渐进收口。
4. 去掉打印/进度条耦合：`tqdm` 保留但可被 context 关闭。
5. 异常规范化：内部 `raise RuntimeError(...)` 保留原样，**公开 API 出口**统一包装为契约层异常家族。
6. 文件头版权：保留原 `Date/Desc/URL` 注释，追加搬运标注（§5.5）。
7. **不做"顺手重构"**：搬运文件保持与上游尽可能一致，便于日后 diff 同步。
8. **字符串常量改写**：`"akshare.data"` 等字符串形式的包引用一并改写（否则 CI 通过但运行时断链）。
9. **凭证处置**：上游硬编码 token 替换为环境变量，或在 `port-report.md` 登记并加 `# SECURITY: do not port`。

**公开 API 命名**：沿用 akshare 原名、去掉 `akshare` 前缀（`opendata_http.stock_zh_a_hist(...)`）。语义化入口由上层提供（REST/WS + ProviderRegistry 路由）。`opendata_fuyao` 与 provider **不套用** akshare 命名。

### 5.3 HTTP 客户端与请求治理（搬运侧细节）

统一客户端 `opendata/data/http_client.py`：

- 会话复用（`requests.Session`）+ 连接池；UA/Referer 可配；
- 超时（连接/读取分别可配，默认保守）；
- 重试：指数退避 + 抖动，仅对幂等 GET；
- 限流：按 host 令牌桶，429/403 触发退避与熔断标记；
- 失败分类：网络 / 超时 / 限流 / 反爬 / 上游错误，产出可诊断信息；
- 可选缓存（§13）；代理支持（海外源必需）。

> 设计取舍：本期不引入 playwright/无头浏览器。`mini_racer` 相关的 JS 解密保留；建议**将 JS 执行隔离到子进程/受限环境**并记录 JS 来源与 sha256（安全审计项，§15 R15）。

## 8. 数仓分层设计（ods / 校对 / dwd）★

### 8.1 ods 层（一源一表，源原始列保真）

- 命名：`ods_<domain>_<source>`；位于 `opendata_data` 库。
- **列结构（v2.0 澄清）**：

| 部分 | 内容 |
|------|------|
| **源原始列** | 保持源命名与类型（仅做类型安全映射，不做语义清洗）——**逐源不同** |
| 元数据列 | `_source` varchar(32) / `_fetched_at` datetime / `_batch_id` char(36) |

> **为什么不是"契约模型推导"**：同 domain 的两个源字段名/单位/口径不同（akshare 中文列 vs 同花顺英文列），若 ods 统一为契约模型，则"原始保真"不成立且源特有字段丢失。契约模型的职责是提供 **dwd** schema 与各源 **field_mapping**。

- 主键：业务 key（如 `(symbol, trade_date)`；域专有 key 由契约模型声明）。
- **DDL 归属（v2.0 钉死）**：数据仓库 DDL 由**独立 alembic 环境**管理（`alembic_data/` + 独立 version 表），迁移作为显式部署步骤执行；应用启动只校验版本不建表。"启动时 ensure-table"仅保留在 development 且需显式开关。
- 写入（`ods_writer.py`，由 `akshare_provider` 演进）：
  - **key 级 upsert**（`ON DUPLICATE KEY UPDATE`），幂等语义 = 同一业务 key 更新；
  - 使用 SQLAlchemy Core 或 raw `text()` + `executemany`，**禁用 ORM 逐对象写入**；
  - 大批量走 **staging 表 + `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`**，按标的/按年切片流式处理（内存恒定）；
  - commit 粒度 5 万~10 万行；
  - **修正现有两处缺陷**：① 自动建表无主键/唯一键导致 upsert 永不触发；② 用内容哈希 `row_hash` 做唯一键导致"价格修正 = 新增一行"。
- **大表分区（v2.0 补运维）**：日线类大表按 `trade_date` 做 **`RANGE COLUMNS(trade_date)` 年分区 + `MAXVALUE` 兜底分区**；约束：所有唯一键必须包含分区键。
  - **分区维护任务**：每日检查 `information_schema.PARTITIONS`，最新分区上界 < 当前年 + 2 时执行 `REORGANIZE PARTITION pmax INTO (...)`；写入调度模板为**强制任务**。
  - 无分区键谓词的查询（如仅按 symbol）会扫描全部分区 → API 层强制默认时间窗。
  - 分区表不支持外键与全文索引（登记为约束）。
- **schema 演进**：源端新增列默认忽略并记录；加列走显式迁移，不自动 ALTER。
- **`/tables` 兼容**：ods 表无 `id` 列，现有 `ORDER BY id` 分页需改为按业务主键排序或独立分支。

### 8.2 交叉校对

- 触发：pipeline 内**落库后即时**校对（增量窗口）；另支持手动全量校对任务。
- **比对路径（v2.0 修订）**：**经契约模型归一化后比对**
  ```
  ods(源A) → field_mapping → 契约模型 ┐
                                      ├→ 按业务 key 逐字段比对 → dq_diff_report
  ods(源B) → field_mapping → 契约模型 ┘
  ```
- **口径映射表**（每域显式声明，A4 交付物）：
  - 字段映射（`开盘` ↔ `open`）
  - 单位换算（成交量 手→股 ×100；成交额 →元）
  - 复权口径（默认只比对 raw；复权序列需先统一因子基准）
  - key 规范化（`600519` ↔ `600519.SH`）
  - 停牌/缺失语义（两源皆缺视为一致，单源缺视为 `missing`）
  - 差异率分母口径（取双方 key 并集）
- 规则（可配置）：数值字段相对误差 ≤ 阈值（默认 1e-6；价格类可设 1e-4）→ 一致；日期/字符串精确相等；单侧缺失行或超阈 → 差异。
- 产出 `dq_diff_report`（**落数据仓库库**）：domain / source_a / source_b / biz_key / field / value_a / value_b / deviation / verdict / checked_at / batch_id。
  - **默认只存聚合统计 + 抽样明细**（阈值可配），全量明细走导出文件——避免千万行级明细冲垮主库。
- **告警治理（v2.0 新增）**：
  - 已知差异模式白名单（按 domain+field 登记容忍项）；
  - 按 diff fingerprint 去重（连续相同差异不重复告警）；
  - 告警分级（差异率突增才升级）。
- 告警通道：SMTP 邮件 + WS `data.diff_alert`。
- **反例用例**：字段名不匹配时必须报错而非静默通过；单位未归一时必须产生 mismatch。

### 8.3 dwd 合并层

- 命名：`dwd_<domain>`；列结构 = 契约标准化模型字段 + 留痕列：

| 列 | 说明 |
|----|------|
| `source` | 本行实际来源（权威源或降级源） |
| `_merged_at` | 合并时间 |
| `_diff_flag` | 0=多源一致或单源；1=存在差异（关联 dq_diff_report） |
| `_as_of` | **数据版本日期（point-in-time）**，支撑回测复现 |

- 合并规则：按权威度逐行取数；数值差异不改变取值（仍取权威源），仅置 `_diff_flag=1`。
- **复权口径整段同源（D10）**：同一查询窗口内的复权因子不得混源。
- **修订传播（v2.0 新增）**：合并单元 = **增量窗口 ∪ 受影响 key 集合**（ods upsert 返回的受影响主键）——确保被修正的旧 key（复权重算、财务重述）能传播到 dwd；另设**周期性全量重建**（如每周日）作为一致性收敛手段，登记为调度模板任务。
- **单源域恒启用（v2.0 修订）**：单源数据域的 dwd 以直通模式生成（VIEW 或薄表），保证 `layer=dwd` 契约统一、WS 推送时机统一。原"第 3/4 步多源才启用"改为"**恒启用；单源域为直通模式**"。
- 查询默认层：REST/WS 默认读 dwd；`layer=ods` 显式指定时按源查询。

### 8.4 既有数据表迁移

- `akshare_data` 库中既有按脚本名建的表：新建 ods 表并行落地期间**旧表保留只读**。
- **验收阶段执行转移评估**：比对旧表与新 ods 表的覆盖度——
  - 有增量价值：执行迁移脚本（补 `_source`/`_fetched_at`/`_batch_id`），以 upsert 写入，**key 冲突以新抓为准**；
  - 已被 market-dumps 全量覆盖：跳过迁移，旧表导出归档；
  - 验证行数与抽样一致后 **DROP 旧表**。
- **注意**：现有旧表的主键结构（`R_ID` 自增 / `row_hash` 唯一键）**不可直接分区**，迁移实为"建新表 + `INSERT...SELECT` 重映射 + 校验 + RENAME 切换"。

### 8.5 容量测算与保留策略（v2.0 新增）★

**行数与存储估算**：

| 域 | 行数量级 | 存储估算 | 承载方案 |
|----|---------|---------|---------|
| A 股日线 × 单源（10 年） | 5,400 × 250 × 10 ≈ **1,300 万行** | ≈ 1.5 GB | MySQL + 年分区 |
| A 股日线 × 双源 + dwd | ≈ **3,900 万行** | ≈ 4.5 GB | MySQL + 年分区 |
| 期货日线（约 70 品种 × 10 年） | ≈ 20 万行 | 小 | MySQL |
| 财务/指数成分/元数据 | 百万级 | 小 | MySQL |
| **A 股分钟线 × 单源（10 年）** | 5,400 × 250 × 240 × 10 ≈ **32 亿行** | ≈ **389 GB** | **Parquet 文件 + 元数据索引（D13）** |
| A 股分钟线 × 双源 + dwd | ≈ 97 亿行 | ≈ 1.17 TB | 同上 |

**决策（D13）**：分钟线**不进 MySQL**，走 Parquet 文件（分区路径 `domain/symbol/year`）+ 主库元数据索引表；REST 对分钟线走文件查询。

**写入性能预算**：日线单源 1,300 万行批量 upsert 需在 A4 阶段实测并记录基准（目标：小时级完成，内存恒定）。

**保留策略**：

| 数据 | 保留 |
|------|------|
| 日线、财务、元数据 | 永久 |
| 分钟线 | N 年（可配） |
| 缓存（原始响应） | TTL（可配），不写版本库 |
| `dq_diff_report` | 聚合数据保留 N 天，明细走导出文件 |

**选型触发阈值**：单表 >5,000 万行 或 校对查询 P95 >10s → 启动存储演进评估（候选：列存 / DuckDB / ClickHouse 旁路）。

## 9. 跑批与调度设计

### 9.1 pipeline 编排

```
DataPipeline(domain, source)
  ├─ 1 fetch        经 ProviderRegistry 路由 Fetcher（增量窗口 or 全量回补）
  ├─ 2 ods upsert   ods_writer 写 ods_<domain>_<source>（返回受影响 key 集合）
  ├─ 3 cross-check  对增量窗口 ∪ 受影响 key 校对 → dq_diff_report（单源域跳过）
  ├─ 4 dwd merge    合并重算该 domain 的 dwd（**恒启用**；单源域为直通）
  ├─ 5 ws push      广播 DataUpdateEvent（§10.2）
  └─ 6 meta 登记    data_tables / 执行统计（沿用 task_executions）
```

- 复用现有能力：线程池执行、`task_executions` 记录、`/ws/executions` 状态推送、RetryService 重试。
- 每步幂等、失败可从当前步重入（步级检查点）。
- **单标的失败不阻断全局**；失败清单可导出，且前端提供**一键重试**。

### 9.2 断点续拉与进度持久化

- 新表 `pipeline_progress`（主库）：`pipeline_id / domain / source / shard（标的分片）/ window / status / updated_at`。
  - 职责边界：`task_executions` = 调度执行记录（对外展示）；`pipeline_progress` = 分片级断点状态（内部续跑）。
- 大任务按标的分片（如 500 标的/片）登记进度；重启后跳过已完成分片。
- **水位真相源（v2.0）**：增量判断**以 ods 已有区间为唯一水位来源**（`SELECT MAX(trade_date)` / 区间 diff）；文件缓存仅用于 market-dumps 等大文件下载暂存，不承担水位职能。

### 9.3 调度配置与部署拓扑（D8）

- `scheduled_tasks` 表新增 pipeline 型任务（type=pipeline，payload 含 domain/source/窗口策略）。
- 内置 P0 模板：A 股四件套双源每日增量（收盘后错峰）、周末全量校对、**分区维护**、**新鲜度检查**。
- **调度时间业务校准**：17:00/18:00 的错峰需**真机实测后调窗**（akshare 当日日线未必已更新），否则会出现"成功执行但没拿到当日数"。
- **部署拓扑（v2.0 决策）**：
  - 本期定位 **单进程合一部署**（API + scheduler + WS 同进程，`WORKERS=1`）；**多 worker 列为非目标**。
  - 调度归属由显式配置 **`ENABLE_SCHEDULER`** 控制；生产模式下未显式配置则**启动即失败**（不再依赖 `workers > 1` 推断，消除静默禁用）。
  - 防重采用**进程内锁**（单进程下即足够）；分布式锁随多 worker 能力一并后置。
  - **演进项**：当跑批影响 API 响应时，拆出独立 worker 进程（同镜像不同启动命令），跨进程推送改走 Redis pub/sub。
- **Redis 不可用时的降级**：明确为"**禁用 scheduler + 告警 + 人工介入**"（消除多 worker 各自启用导致的裂脑）。

### 9.4 业务操作界面（v2.0 新增）★

| 能力 | 说明 | 交付 |
|------|------|------|
| **任务向导** | 选域 → 选源 → 选频率 → 预览将生成的表与首次回补范围 → 保存（至少覆盖 P0 域） | B3 |
| **执行详情增强** | 分片进度条（3,200/5,500 只）、预计剩余时间、失败清单展示与**一键重试** | B3 |
| **market-dumps 一键导入** | 前端可触发，作为业务第一次看到"全市场数据进仓库"的演示时刻 | A3/A4 |
| **数据目录页** | 按数据域组织：覆盖标的数、时间范围、各源最近更新、新鲜度、质量标记 | B4 |
| **新鲜度视图** | 各域最新数据日期与滞后天数；缺失即告警 | A4 |

## 10. API 服务层设计

### 10.1 REST 查询

- 新路由 `opendata/api/data_query.py`，前缀 `/api/v1/data`：

```
GET /api/v1/data/{asset_class}/{domain}
    ?symbols=600519,000001      # 标的（可选，缺省=全市场）
    &start=2020-01-01&end=2026-09-22
    &source=auto|akshare|ths|yfinance|...
    &layer=dwd|ods              # 默认 dwd
    &adjust=none|qfq|hfq        # ★ v2.0 新增，默认 none，服务端计算（D10）
    &period=&report_date=       # ★ 财务域专有（报告期/公告日/重述取舍）
    &fields=open,close,...      # 可选字段过滤（白名单校验）
    &page=&page_size=           # 分页（上限保护）
GET /api/v1/data/capabilities           # 注册表能力清单
GET /api/v1/data/sources                # 源清单与权威度
GET /api/v1/data/catalog                # ★ 数据目录（capabilities + freshness 合并）
GET /api/v1/data/domains/{domain}/freshness      # ★ 新鲜度
GET /api/v1/data/domains/{domain}/diff-report    # 校对差异报告查询
```

- **参数安全（v2.0 新增）**：
  - `fields` 必须对该表实际 schema 做白名单校验（`INFORMATION_SCHEMA.COLUMNS` 或契约模型字段集），否则 400；
  - `layer` / `source` / `adjust` 使用枚举；
  - `symbols` 走绑定参数（`IN (...)`），不拼字符串；
  - 导出时对 CSV 公式注入前缀（`=`/`+`/`-`/`@`）做转义；
  - **默认时间窗**：不带日期区间的查询强制默认窗口（避免全分区扫描）。
- 响应：标准化模型 schema（OpenAPI 生成）；大数据集分页 + 异步导出。
- 鉴权：JWT（沿用）+ API Key（§10.3）；限流沿用 slowapi。

### 10.2 WS 订阅

- 新路由 `opendata/api/data_subscribe.py`：`WS /ws/data/subscribe`。
- **协议（v2.0 修订：meta 为一等公民）**：

```jsonc
// client → server
{"action": "auth", "token": "..."}                    // ★ 首帧认证（连接后 5s 内，替代 query token）
{"action": "subscribe", "domain": "stock_daily", "symbols": ["600519"], "layer": "dwd",
 "payload": "meta",                                    // 默认 meta
 "since_batch_id": "..."}                              // ★ 可选：补发断线期间的 meta 事件
{"action": "unsubscribe", "domain": "stock_daily"}

// server → client
{"type": "data.update", "domain": "stock_daily", "source": "ths",
 "batch_id": "...", "window": {"start": "...", "end": "..."}, "rows": 4210,
 "payload": "meta"}                                    // meta：仅通知，客户端按需 REST 拉取

// full 模式（实验性，消费方自担分帧拼装成本）
{"type": "data.update", ..., "payload": "full", "chunk": {"chunk_id": "uuid", "seq": 1, "total": 7}, "data": [...]}

{"type": "data.diff_alert", "domain": "...", "mismatch_ratio": 0.012, ...}
{"type": "error", "code": "...", "message": "...", "suggestion": "..."}   // ★ 含业务文案与处置建议
```

- **批次水位与补发（v2.0 新增）**：维护批次水位表（`batch_watermark`），`subscribe` 支持 `since_batch_id` 补发 meta 事件——解决断线期间事件永久丢失、消费方只能盲拉的问题。
- **认证（v2.0 修订）**：**迭代 1B 前完成升级**——首帧认证或 `Sec-WebSocket-Protocol` 承载 token；nginx 对 `/ws/` 关闭查询串记录。不再使用 query token。
- **full 模式兜底**：单帧上限 5000 行且 ≤2MB，超限自动分帧；极端总量（>10 万行或 >10MB）强制降级 meta 并附 `truncated: true`。
- 连接管理：30s 心跳、90s 空闲断开；每连接订阅上限（默认 10 个 domain）；积压超限（推送队列 > 1000）降级 meta 并告警。

### 10.3 消费方 API Key

- 新表 `api_keys`（主库）：`key_hash`、`name`、`owner_user_id`、`scopes`（数据域白名单）、`rate_limit`、`status`、`last_used_at`、**`expires_at`**、**`rotated_at`**。
- **存储规格（v2.0 明确）**：明文 Key 用 `secrets.token_urlsafe(32)`（≥128 bit 熵）；存储 `sha256(pepper + key)`（pepper 来自环境变量）；查找用等值索引；比较用 `hmac.compare_digest`；认证失败统一延迟 + 限速防枚举；支持过期与轮换。
- 认证依赖：请求头 `Authorization: Bearer od-<key>` 或 `X-API-Key`；与 JWT 共存（优先识别 API Key）。
- 管理接口：`/api/v1/keys` CRUD（admin 或本人）；创建返回明文 Key。
- **落地时点：迭代 1B 随 REST 一起交付**（原 M7 提前，给消费方对接留返工余量）。

### 10.4 客户端与文档

- **最小 Python 客户端 `opendata_client/`**（仓库内目录，git 依赖安装，不发 PyPI）：
  - 封装 REST 分页、认证（JWT / API Key）、`adjust` 参数；
  - `client.stock_daily(symbols, start, end, adjust="qfq")` 级别的调用；

## 12. 上游同步机制

- `opendata_http/upstream.lock`：

```toml
[upstream]
repo = "https://github.com/akfamily/akshare"
commit = "<40位 sha>"        # 基线由 D9 冻结
ported_at = "2026-09-22"

[files."opendata_http/utils/func.py"]
upstream = "akshare/utils/func.py"
sha256 = "..."
manual_edits = false
```

- `scripts/codemod/fetch_upstream.py --diff`：拉取上游新版本，输出"新增/修改/删除"清单与**关键函数签名 diff**。
- 同步流程：`diff → 评估 → port_module 重跑（跳过 manual_edits）→ 对照 → 提交`。
- **fork 维护预算**：每迭代预留 **10~15% 人力**用于上游同步与失效修复（写入实施计划）。
- **manual_edits 最小化**：请求层收口降级为渐进收口（§5.2 规则 3），使绝大多数文件保持逐行可 diff。
- 同花顺：记录文档抓取日期与端点清单快照，端点变更时更新映射表并 bump 版本。

## 13. 缓存与增量

- **缓存根**：`OPENDATA_CACHE_DIR`（默认 `~/.cache/opendata`；Windows 用 `%LOCALAPPDATA%`）。
- **缓存内容（v2.0 修订）**：**只存原始响应**（不缓存标准化/复权结果）——前复权价格会因后续除权除息整体重算、财务数据会被追溯调整，"已收盘区间不可变"的前提不成立。
- **缓存键**：`source + endpoint + 规范化参数 + adjust_basis + as_of + schema_version`。
- **水位真相源（v2.0 新增）**：增量判断**以 ods 已有区间为唯一来源**；文件缓存不承担水位职能，避免"缓存有而 ods 没有 / 反之"两个真相源打架。
- **批量与续拉**：

```
fetch_many(requests=[FetchRequest(...), ...],
           concurrency=4, cache=True,
           on_error="continue")   # 单标的失败不阻断
```

- 进度持久化到 `pipeline_progress`（按标的分片 pending/done/failed），重跑时跳过 done。
- 限流联动：缓存命中不发请求；批量任务按源 QPS 令牌桶节流。
- **point-in-time**：ods/dwd 增加数据版本列，REST 支持 `as_of=` 参数，支撑回测复现。

## 15. 风险与应对

**技术风险**

| # | 风险 | 应对 |
|---|------|------|
| R1 | 爬虫接口易碎 | upstream.lock + 同步工具 + **P0 域每日健康巡检**；失效接口健康标记，路由自动降级 |
| R2 | 搬运工程量 | codemod 自动化 + **按需搬运（D9）** + 分域递进 |
| R3 | 同花顺限流/窗口上限 | 退避 + market-dumps 批量通道 + 分页分段 |
| R4 | AGPL 合规 | §1.3 隔离机制 + 审查留档 + CI 断言 |
| R5 | BSL/MIT 混合许可 | 物理分包 + `registration.py` 移出 + MIT 子树可独立运行 + THIRD_PARTY_NOTICES |
| R6 | 旧机制迁移牵动前端 | 兼容期开关 + 迭代 1B 统一收口 |
| R7 | 全量回补写入性能 | staging 表 + 批量写入 + InnoDB 调参（`innodb_buffer_pool_size` ≥4G）；A4 写入基准测试 |
| R8 | WS 推送积压 | meta 一等公民 + 分帧兜底 + 订阅上限 + 积压告警 |
| R9 | **数据再分发合规** | 权利登记表 + 免责声明 + 授权话术定位"软件授权"（§1.3） |
| R10 | **分钟线容量击穿 MySQL** | D13 走 Parquet + 元数据索引；选型阈值监控 |
| R11 | **JS 执行安全面**（40 个文件用 mini_racer 执行站点 JS，与 API 同进程） | 迭代 1A 增加一次性 bandit 全量扫描（含 B 层）并 triage 留档；JS 执行隔离到子进程并记录来源与 sha256 |
| R12 | 权威源单点（同花顺商业 Key） | Key 配额/到期/封禁监控告警；第二权威源预案 |
| R13 | 上游 akshare 停更 | 冻结基线 + fork 维护预算（每迭代 10~15%）+ "失效即弃" |

### 16.2 遗留观察项（非阻塞）

1. API Key 完整用量报表与按域计费级配额（本期只做基础限速）。
