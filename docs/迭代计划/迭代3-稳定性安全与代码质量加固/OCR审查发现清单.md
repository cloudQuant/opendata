## 2. Critical

### [A] `opendata/core/database.py:168` [security]

Operational/security defect: when `ADMIN_DEFAULT_PASSWORD` is unset, a random password is generated, hashed into the admin row, and then only its first 3 characters are logged. The resulting `admin` account can never be logged into, and because `existing_admin` is non-`None` on every later startup, it will never be re-provisioned — leaving the system with a permanently unusable superuser. At the same time, leaking the first 3 characters of the secret into logs is an unnecessary disclosure. Either require the env var (fail fast at startup) or emit the full generated password exactly once to a secure channel (log at WARNING with the whole value, or write it to a 0600 file) so the credential is recoverable.

### [A] `opendata/core/config.py:435` [security]

The production guard is bypassed when `SECRET_KEY` is unset: Pydantic v2 does not run field validators on default values unless `validate_default=True`, so `Settings()` accepts `DEFAULT_SECRET_KEY` in production. It also reads `APP_ENV` from `os.environ` instead of the already-validated `app_env`, so `APP_ENV=production` supplied only through `.env` is ignored. Add `validate_default=True` to the `secret_key` field, compare against `info.data.get("app_env")`, and reject empty secrets.

### [A] `opendata/services/data_acquisition.py:545` [bug]

`INSERT IGNORE` suppresses every MySQL error, not only duplicate-key conflicts. Combined with the `VARCHAR` length cap inferred from the current DataFrame, later values longer than the inferred column width are silently truncated, invalid values may be coerced, and rows can disappear without surfacing a failure. That is silent warehouse corruption. Use a duplicate-targeted construct (for example `ON DUPLICATE KEY UPDATE id=id`) or handle duplicate-key errors explicitly so real data errors still fail the download.

### [A] `opendata/services/retry_service.py:163` [bug]

Script failures are never detected here. `DataService.execute_script` catches errors internally and returns a result dict with `success: False` (see `opendata/services/data_service.py`), it does not raise. This code unconditionally records the retry execution as `COMPLETED` with `rows_after=result.get("rows_processed")` (which is `0` on failure), so a failed retry is persisted as a success and the retry chain is never continued — a real data-consistency bug. Check `result["success"]` before marking completed (e.g. raise inside the inner `try` so the existing failure path marks the execution `FAILED` and reschedules).

## 3. High

- **`opendata/api/dependencies.py:122-122`** [A/bug] — `payload["sub"]` is passed to `int()` further down without any conversion guard. A token that verifies correctly but carries a non-numeric (or list/None-like) `sub` makes `int(user_id)` raise `ValueError`/`TypeError`, which propagates out of the dependency as an unhandled 500 instead of a 401. This is reachable with any structurally valid JWT signed with the server key (e.g. tokens minted by older/other code paths, or a future issuance bug), so the parsing should fail closed with 401.
- **`opendata/api/auth.py:251-253`** [A/security] — Refresh tokens are never blacklisted, so neither logout nor rotation actually terminates a session: (1) `logout` revokes only the access token, leaving the refresh token issued by the same `_login_payload`/`_register_payload` valid, so a client that "logs out" (or an attacker who stole the refresh token) can keep minting fresh access tokens via `/auth/refresh`; (2) `refresh` neither rejects an already-revoked token nor revokes the presented one while rotating, so every old refresh token keeps working until its own expiry and a leaked token can be used indefinitely in parallel with the legitimate client. The blacklist backend is keyed by token hash and already accepts arbitrary tokens (`revoke`/`is_revoked`), so: in `/auth/refresh`, reject the presented token when `token_blacklist.is_revoked(...)` is true and revoke it (with its `exp`) right before issuing the new pair; in `/logout`, also…
- **`opendata/api/auth.py:360-361`** [A/security] — Changing the password does not invalidate any existing credential: previously issued access tokens keep working until they expire and refresh tokens (including the one belonging to an attacker who stole the old password) keep minting new access tokens. This defeats the main purpose of a password change after a compromise. Revoke the refresh tokens / bump a per-user token version (or compare a `password_changed_at` claim against the token `iat` in `get_current_user`) as part of this operation.
- **`opendata/api/auth.py:92-94`** [A/bug] — Check-then-insert race on a unique column: in `register` (email and candidate usernames), in `create_interface` (`DataInterface.name` is `unique=True`, models/interface.py:84) and in `create_script` (`data_scripts.script_id` is `unique=True`) availability is verified with a separate `SELECT`/ORM pre-check, but the following `INSERT`/`commit()` is unconditional. Two concurrent requests can both pass the pre-check and the loser hits a unique/constraint violation on `commit()`; that `IntegrityError` is uncaught, so the client receives an unhandled 500 (and the session is left in a failed state) instead of the documented 400/409. Wrap the commit in `try/except sqlalchemy.exc.IntegrityError`, `await db.rollback()`, and translate it into the appropriate conflict response — or make the INSERT itself the authoritative guard (`INSERT ... ON CONFLICT`/`INSERT IGNORE`).
- **`opendata/api/data.py:181-183`** [A/security] — IDOR on both read endpoints: `get_download_progress` and `get_download_result` look up any `TaskExecution` by its sequential integer id and never scope the query to the caller (`current_user` is accepted but unused in the result endpoint), so any authenticated user can poll another user's download state (`rows_processed`, `error_message`, timings) or read its result metadata (`rows_affected`, duration, completion time, and on failure the raw `error_message`) simply by iterating ids. `TaskExecution.operator_id` already exists (`opendata/models/task.py`), so once `trigger_download` records the owner, both read paths must filter on it (admins may bypass), ideally through a shared ownership-scoping helper.
- **`opendata/api/keys.py:241-243`** [A/bug] — Check-then-act race on key state: `_authorized_key` only reads the row (plain `db.get`, no `SELECT ... FOR UPDATE`), and `ApiKeyService.revoke/rotate` then re-check `record.status` and commit. Two concurrent rotates of the same key both pass the ACTIVE check and each issues a new key in its own commit, so the caller can end up with two live keys even though rotation is documented to "replace" the key; the same applies to a concurrent revoke+rotate, and two concurrent revokes both report success although the second is documented to return 400. Please make the transition atomic, e.g. have the service perform `UPDATE api_keys SET status='revoked' WHERE id=:id AND status='active'` and verify `rowcount`, or re-read the row with `with_for_update()` inside the same transaction as the mutation, and map the losing request to 409/400.
- **`opendata/api/interfaces.py:183-189`** [A/bug] — Both handlers declare their payload as plain scalar parameters instead of a JSON body: `create_interface` takes `name`, `display_name`, `category_id`, and `update_interface` takes `display_name`, `description`, `is_active`. FastAPI therefore binds all of them as **query parameters**. Clients POSTing/PUTing `{"name": ...}` get a 422 (missing query params); worse, a PUT with a JSON body silently updates nothing (all `None` → no field changed) while still returning `success=True`, and column-level validation constraints (e.g. max length matching the DB columns) are bypassed either way. Declare proper Pydantic request models (`InterfaceCreateRequest`, `InterfaceUpdateRequest`) and accept them as the request body.
- **`opendata/api/data_subscribe.py:178-180`** [A/bug] — Shutdown ordering is unsafe. `session.queue` is bounded (`MAX_BACKLOG`) and the hub deliberately sheds/downgrades when it fills, so `put_nowait(None)` can raise `asyncio.QueueFull` for exactly the slow-consumer case this path must handle. That exception escapes the `finally` and skips `await hub.unregister(subscriber)`, leaving a dead subscriber registered in the hub forever (it keeps matching events and pushing into an orphaned queue). Additionally `writer.cancel()` is not awaited, so the task can still be pending when the event loop tears down and its `CancelledError` is never observed. Put the sentinel in before cancelling, guard the `put_nowait`, and await the cancelled task.
- **`opendata/api/pipeline.py:70-73`** [A/bug] — Run bookkeeping is evicted in the wrong order and read unsafely. Retention iterates `sorted(_RUNS)`, i.e. alphabetically by the random `uuid4().hex[:12]` run id rather than by insertion/recency, so it drops arbitrary entries (possibly the newest) instead of the oldest. Popping a still-running run from `_TASKS` additionally removes the only strong reference to its `asyncio.Task` (which the comment at ~line 155 explicitly relies on), so an in-flight batch can be garbage-collected mid-run while its status becomes 404. Keep the newest N in insertion order (dicts preserve it), and in `_execute_run` read the entry defensively (`_RUNS.get(run_id)` and bail out) instead of `_RUNS[run_id]`, since a `KeyError` in a fire-and-forget task is never observed by any caller.
- **`opendata/api/pipeline.py:143-143`** [A/performance] — No concurrency limit, deduplication or rate limit: each POST spawns another full incremental batch (minutes of DB writes plus outbound provider calls) while the retention cap only bounds bookkeeping. Any authenticated caller can trivially exhaust the connection pool / provider quota by repeating this call. Consider rejecting with 429 when N runs are already in flight, and/or deduplicating an identical in-flight request.
- **`opendata/api/published_access.py:318-319`** [A/bug] — Authorization contract mismatch: API-key `scopes` are defined elsewhere as a domain whitelist (`['*']` = all domains, `[]` = none), not operation grants. A key issued through `ApiKeyCreateRequest` with the documented domain scope (for example `scopes=['stock_daily']`) can never authorize `data.read` here because the operation is not present in `scopes`. The tests mask this by constructing `Principal` objects with mixed values such as `('*', 'data.read')`. Either add a separate operation-permission field that is validated/issued by the key API, or stop requiring the operation in the domain-scope tuple and enforce the operation via the reviewed grant plus an explicit key capability. The same issue propagates to `list_permitted_datasets`, so real API keys will always get an empty catalog.
- **`opendata/api/settings.py:41-42`** [A/security] — Values coming from the request are interpolated verbatim into the `.env` file. A host/user/database containing `\n` (or `\r`) injects arbitrary extra `KEY=VALUE` entries into the environment file; a `#`, quotes, or spaces silently corrupt the value and break dotenv parsing on the next start. The Pydantic models only bound the length, they do not constrain the charset.
- **`opendata/api/settings.py:52-52`** [A/bug] — The docstring claims an atomic write, but this is a plain truncate-and-rewrite: a crash/exception mid-write leaves a truncated `.env`, and two concurrent admin updates (the endpoint is `async`, so interleaving is possible) read-modify-write the same file and silently drop each other's keys. Additionally, a newly created `.env` inherits the default umask (typically 0644, world-readable secrets), and any `OSError`/`PermissionError` here (e.g. read-only deployment path) escapes as an unhandled 500 after the config was already reported as updated.
- **`opendata/api/settings.py:169-169`** [A/performance] — This `except ImportError` fallback runs fully synchronous, blocking I/O (`create_engine` + `connect()` + `execute()`) inside an `async def` handler, stalling the whole event loop for the duration of a TCP connect to an arbitrary host with no `connect_timeout` (default is infinite for pymysql). The created `Engine`/`QueuePool` is also never disposed, so every call leaks a pooled connection until GC. Either drop the sync fallback (aiomysql is already the primary driver) or offload it via `await asyncio.to_thread(...)` with a timeout and `engine.dispose()` in a `finally`.
- **`opendata/api/tables.py:50-52`** [A/security] — The XLSX path passes raw database strings to pandas/openpyxl. openpyxl treats a cell beginning with "=" as a formula, so externally acquired data such as "=cmd\|'/c calc'!A0" can execute when the exported workbook is opened. The CSV path already neutralizes this via serialize_for_csv/escape_csv_formula; apply the same string sanitization (or write cells explicitly as text) before building the DataFrame.
- **`opendata/api/tables.py:443-445`** [A/bug] — The physical DROP TABLE is committed before the metadata row is deleted. If the later metadata delete/commit fails, the registry still advertises a table whose data has already been destroyed, leaving a stale/inconsistent entry until a retry succeeds. Make this a single recoverable operation (e.g. delete/mark metadata first or add explicit compensation/idempotent cleanup) so a partial failure cannot leave orphaned metadata.
- **`opendata/api/tasks.py:115-116`** [A/bug] — The validated pipeline parameters assigned in `update_task` are silently discarded here: `_apply_task_update` runs afterwards and re-writes `task.parameters` with the raw, unnormalized `request.parameters`. For partial updates (`task_kind` omitted) the `TaskUpdateRequest` validator does not validate pipeline parameters, so the endpoint-level validation is the only gate — and its normalized result (e.g. `"limit": "100"` coerced to `100`) is lost before persistence. Skip this field for pipeline tasks (or apply `request.parameters` before the pipeline validation block) so the validated payload is what gets stored.
- **`opendata/api/users.py:147-150`** [A/bug] — The last-admin safeguard only exists in `delete_user`; `update_user` lets an admin demote the only admin (or set `is_active=False` on them), which locks every administrator out of the system. This also covers an admin demoting/deactivating themselves. Mirror the delete-path invariant here (count remaining *active* admins before applying the change).
- **`opendata/api/users.py:195-196`** [A/bug] — The docstring promises that deleting a user also deletes "all associated tasks and data", but nothing here does that: in `opendata/models/task.py` both `user_id` FKs point to `users.id` with no `ondelete="CASCADE"` and the `User` model declares no relationships/cascades (only `api_keys` has a DB-level cascade). Deleting any user that owns tasks therefore raises an `IntegrityError` from `commit()`, which is unhandled and surfaces as a 500. Either delete the dependent rows explicitly (tasks/sub-tasks/schedules) or add DB-level `ON DELETE CASCADE` plus catch `IntegrityError` and map it to a 409 with a rollback.
- **`opendata/api/websocket.py:52-55`** [A/other] — `broadcast` performs network I/O (`await ws.send_text(...)`) while holding `self._lock`. Consequences: (1) `connect()`/`disconnect()` block until every send completes, so a client that stops reading (TCP backpressure) can stall new connections and all other broadcasts indefinitely; (2) with N clients, cost is O(N) latency chained inside a lock. Snapshot the connection list under the lock, then send outside it. Consider also bounding each send with a timeout so one stalled peer cannot delay the rest.
- **`opendata/api/stock_daily_publication.py:457-458`** [A/bug] — This catch converts every `PublicationStore.get_snapshot` failure into 503. `get_snapshot` deliberately raises `SnapshotExpiredError` for expired snapshots and `SnapshotError` for invalid/missing snapshot metadata; those are mapped to 410/422 by `_ErrorEnvelopeRoute` elsewhere. Because `_read_page` does not swallow them, the same expired snapshot returns 503 on the lookup path but 410 if it expires before page read. Unexpected bugs are also hidden. Re-raise the snapshot-domain exceptions and let the route mapping handle them; only unexpected failures should become 503.
- **`opendata/core/database.py:187-189`** [A/bug] — Check-then-act race under concurrent startup: existence is read with a `SELECT`, then the missing rows are inserted. Two instances booting simultaneously (uvicorn workers, k8s replicas, `--reload` + scheduler) both observe an empty/partial table and both insert, so the loser hits a duplicate-key error on `interface_categories.name` and `init_db()` aborts startup — exactly the failure mode the surrounding comment claims to have fixed. Make the provisioning atomic (single-worker/advisory lock around init, or `INSERT ... ON DUPLICATE KEY UPDATE` / `INSERT IGNORE` on the unique name index) and/or catch `IntegrityError`, roll back and retry once.
- **`opendata/api/temporal_identity.py:426-431`** [A/bug] — `registry.assignments` is ordered pair-major (`(pair, valid_from)`), not globally chronological. For an `instrument_id` selector, the `cursor`-based overlap check below assumes date order; a valid non-overlapping pair handoff where the later-sorting pair starts earlier can be seen as `segment_start < cursor` and incorrectly rejected as ambiguous (422). Sort the matching instrument assignments by `valid_from` (or use the registry's per-instrument index / drop the precheck and rely on the post-resolution segment check).
- **`opendata/core/security.py:50-51`** [A/bug] — `bcrypt.checkpw` raises `ValueError` ("Invalid salt") when the stored hash is not a well-formed bcrypt hash (e.g. empty/NULL-ish column, legacy hash from another scheme, truncated value after a bad migration). Nothing catches it here, so a single corrupted user row turns the login/change-password endpoints into a 500 instead of a clean "invalid credentials" response. Catch `ValueError` and return `False` (log at warning without leaking the hash).
- **`opendata/core/token_blacklist.py:76-77`** [A/bug] — `_periodic_cleanup()` unconditionally re-arms the timer in `finally`, so `stop()` is ineffective: if `stop()` is called (e.g. during app shutdown/tests) while a cleanup pass is running or just before the `finally` block executes, a new daemon `Timer` is created afterwards and the cleanup loop keeps running forever — a leaked thread that retains the whole blacklist. There is also no guard against `revoke()`/`is_revoked()` being used after `stop()`. Add a `_stopped` flag (set in `__init__`, flipped in `stop()`) and skip re-arming when set.
- **`opendata/core/config.py:293-295`** [A/security] — `api_key_pepper` is explicitly a secret but is declared as a plain `str` without `repr=False`/`exclude`; `BaseSettings.__repr__` and `model_dump()` can expose it in logs or diagnostics. The same applies to `fred_api_key`, `smtp_password`, `mysql_password`/`data_mysql_password`, and `secret_key`, whereas `fuyao_api_key` is already protected. Use `SecretStr` plus `repr=False, exclude=True` consistently and call `get_secret_value()` at use sites.
- **`opendata/core/config.py:300-301`** [A/bug] — This value is passed directly to `asyncio.sleep` in `opendata/api/dependencies.py` (lines 184 and 192). With no lower bound, a negative value raises `ValueError` and turns every failed API-key authentication into a 500 instead of 401/403; a huge or non-finite value is also a self-DoS lever. Add `ge=0.0`, `allow_inf_nan=False`, and a reasonable upper bound.
- **`opendata/core/api_key_rate_limit.py:287-289`** [A/security] — When Redis is not configured this silently enforces limits in per-process memory; with the supported multi-worker deployment (settings.workers > 1) the effective quota becomes workers × limit, so clients can bypass the intended limit by spreading requests across workers. Add the same multi-worker warning/guard used by the token blacklist, or require a shared backend when more than one worker is configured.
- **`opendata/core/api_key_rate_limit.py:224-224`** [A/bug] — The Redis client is created without socket_connect_timeout/socket_timeout, and check() awaits eval on the API-key authentication path. A black-holed Redis can therefore hold every keyed request for the OS TCP timeout (or indefinitely for an established but unresponsive connection), preventing the intended fail-closed 503; configure finite connect/read timeouts for this client.
- **`opendata/models/data_script.py:67-67`** [A/bug] — `Enum(ScriptFrequency)` without `values_callable` persists the enum **names** (`"HOURLY"`, `"DAILY"`, … — as the migration `2026_09_22-0001_initial_schema.py` confirms), yet `to_dict()` below exposes `self.frequency.value` (lowercase `"daily"`) and the afi_port `DataScriptCreate`/`DataScriptUpdate` schemas type `frequency` as a free-form `str`. SQLAlchemy resolves bind values against the *name* lookup, so a client that reads `"daily"` from the API and writes it back (or sends `"daily"` on create) hits `LookupError: 'daily' is not among the defined enum values` at flush time — a 500 for a client-side validation error. Either coerce/validate incoming strings to `ScriptFrequency` at the schema/service boundary, or switch the column to values via `values_callable` (requires a migration since existing rows hold uppercase names).
- **`opendata/services/data_service.py:80-81`** [A/bug] — `asyncio.wait_for` does not raise the builtin `TimeoutError` on Python 3.10 (the project declares `requires-python = ">=3.10"`): there `asyncio.TimeoutError` is `concurrent.futures.TimeoutError`, which inherits from `Exception`/`OSError`-unrelated, so it is **not** a subclass of the builtin `TimeoutError`. On 3.10 this handler is therefore dead code: an outer timeout falls through to the generic `except Exception` block, and since `str(asyncio.TimeoutError())` is an empty string, the caller gets `{"success": False, "error": ""}` with no indication that a timeout occurred (and no "timed out after Ns" semantics). Always catch `asyncio.TimeoutError`, which is an alias of the builtin on 3.11+ and correct on 3.10.
- **`opendata/services/data_service.py:78-78`** [A/bug] — The success path returns the inner `ScriptService.execute_script` dict verbatim, but that dict only contains `success`, `script_id`, `execution_id`, `result`, `error` — it has no `rows_processed` key, although the docstring (and the timeout/exception branches below) promise it. Callers rely on it: `RetryService` does `rows_after=result.get("rows_processed")`, so on every successful execution `rows_after` is persisted as `None`, i.e. the recorded row count for retried executions is lost. Normalize the success payload so all branches return the same key set (derive the count from the script result where possible, otherwise `0`).
- **`opendata/models/task.py:159-159`** [A/bug] — `to_dict()` dereferences enum values directly (`self.schedule_type.value`, and the same pattern is used in `TaskExecution.to_dict`/`__repr__`). SQLAlchemy `default=` values are applied only at INSERT/flush, so a freshly constructed `ScheduledTask(...)` that did not pass `schedule_type=` explicitly still has `schedule_type is None` and this line raises `AttributeError: 'NoneType' object has no attribute 'value'`. The same applies to `task_kind`, `is_active`, `retry_on_failure`, `max_retries` and `timeout`, which would be serialized as `null` instead of their documented defaults. Serialize defensively (or set the defaults on the instance before flush).
- **`opendata/models/task.py:281-281`** [A/bug] — Same pre-flush enum problem as in `ScheduledTask.to_dict`: `status` and `triggered_by` use Python-side `default=` values that are only populated at flush, so calling `to_dict()` on a not-yet-flushed `TaskExecution()` (a common pattern in tests/services that build the object first) raises `AttributeError` here rather than returning `"pending"`/`"scheduler"`.
- **`opendata/services/corporate_events.py:490-493`** [A/other] — `ingest`/`drain_pending` are `async` but they invoke the synchronous SQLAlchemy path (`record_version`, `claim_pending_jobs`, `complete_jobs`, `retry_jobs`) directly on the event loop. Only `factor_builder.build` is offloaded via `asyncio.to_thread`, so every DB round-trip (plus the whole per-symbol commit/retry sequence) blocks the loop — in FastAPI that stalls all other requests for the duration of the drain. Wrap the store calls in `await asyncio.to_thread(...)` (or make the store async) so the claim/complete/retry I/O does not block the loop.
- **`opendata/services/data_acquisition.py:526-535`** [A/bug] — `astype(str)` flattens typed values: `None`/NaN and the literal strings `"None"`/`"nan"` serialize identically, and `"\|".join(...)` is ambiguous whenever a value contains `\|`. Distinct source rows can therefore produce the same `row_hash`, and the UNIQUE constraint causes one of them to be silently ignored. Use a canonical, type-preserving serialization before hashing, such as JSON with explicit nulls, or length-prefix each field.
- **`opendata/services/data_acquisition.py:377-383`** [A/other] — `asyncio.wait_for` cancels only the `Future` returned by `run_in_executor`; it cannot stop the blocking worker thread. A hung akshare call keeps occupying one of the eight `_akshare_executor` workers, so repeated timeouts exhaust the pool and later fetches queue indefinitely (and a hung non-daemon worker can block process exit). Also, the project supports Python 3.10, where `wait_for` raises `asyncio.TimeoutError`, so `except TimeoutError` does not catch it. Catch `asyncio.TimeoutError` at minimum, and use a killable process/subprocess or bounded health-check strategy for real timeout enforcement.
- **`opendata/services/data_acquisition.py:688-691`** [A/bug] — `cancel_execution` only removes the progress-tracking entry. The `execute_download` coroutine and the blocking akshare thread continue running, can still commit warehouse data, and can still overwrite the execution status, while the caller is told cancellation succeeded. Store the task/cancellation token and cancel/await it, or rename this to an untrack operation and stop returning `True` as though the execution was actually cancelled.
- **`opendata/services/data_acquisition.py:491-499`** [A/bug] — `columns_defs` can already contain `id`, `created_at`, or `row_hash` from the upstream DataFrame. The code then appends the same system columns, producing duplicate column definitions (or a duplicate primary key) and causing `CREATE TABLE` to fail; for `row_hash` specifically, `_insert_data` also overwrites the source column. Reserve and validate these names before building the DDL, and rename or reject conflicts.
- **`opendata/services/interface_loader.py:75-79`** [A/bug] — The dedup relies on a DB round-trip, but `async_session_maker` is created with `autoflush=False` (see `opendata/core/database.py`), so newly added-but-uncommitted `DataInterface` rows are invisible to this `select`. Capabilities are keyed by `asset_class:domain:period:market:source` in the registry, so the same `domain` can appear several times in `capabilities()` (the module docstring explicitly says such capabilities "fold into one row"). The second occurrence will therefore pass this existence check and `db.add()` a row with a duplicate `name`, violating the `unique=True` constraint on `DataInterface.name`.
