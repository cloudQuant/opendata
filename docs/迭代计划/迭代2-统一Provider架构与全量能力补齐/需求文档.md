## 1. 目标与范围

目标是一个统一的自研数据获取框架：Provider → QueryParams → Fetcher → 标准模型 → 注册/源路由 → ODS/校对/DWD → REST/WS/SDK。34个provider共用框架，目录独立、能力与依赖独立、失败互不扩散；不强制分别发行。

固定OpenBB范围为32个provider、350个provider×模型条目；AkShare和THS作为另外两个自有来源，维持已实现能力并补迭代1明确欠项。完整清单中的每条都必须有实现或可审阅的复用结论、参数/字段契约及验收记录。上游不可达不取消实现任务，真实对照按实际状态记账。

2026-10-08用户明确执行顺序：先完成全部开发与离线验收，真实来源与部署验收之后单独安排。这是阶段顺序调整，FR2/NFR2身份和完整34/350/202范围保持。当前阶段用受控合成transport、实际隔离存储、安装产物及独立正反例证明实现；实际来源许可、Key、可达性、官方样本和生产环境证据留待后续阶段，不以离线PASS冒充SOURCE_VERIFIED或DEPLOYMENT_VERIFIED。

沿用迭代1FR-2/3/7的统一契约与路由、FR-10/11/12/13的数仓流程、FR-15/16/19/20的服务化、NFR-7质量门禁。当前用户的目录整合要求更新旧“顶层transport分包”的布局决定；许可、来源保真和功能边界继续保留。

## 4. 状态与完成定义

开发完成需具备真实取数代码、已审阅契约、离线正反例、注册/查询入口、声明完整的依赖、打包/资源检查与来源依据。空壳类、NotImplementedError、始终空列表、固定样本返回、只写元数据都不算实现。

SOURCE_VERIFIED要求相应源的真实原始响应及官方事实对照，绑定代码/样本/时间/环境；DEPLOYMENT_VERIFIED要求指定部署环境的实际链路证据。当前verified字段的迁移不自动证明新模型，也不由provider整体转正替代逐能力状态。

模型清单中的NOT_ASSESSED表示当前未做逐模型等价判断，不表示现有代码均不存在。已证明等价的条目可以复用现有实现，但必须记录对应能力与证据，不能按“一个域对应多个模型”直接勾完。

Key评估在2B开工前覆盖15源/195条声明凭据的暴露面，并核对其余17源的底层访问条件；免费/付费档位、配额和实际申请意向均未核实时保持待评估。未申请者可计划DEV_DONE-only交付，live状态仍为NOT_RUN或具体BLOCKED，迭代整体不因此转PASS；付费采购另需预算授权。

权利、Key、开发、真实验证分别记账。现有登记表v1.2对具体源/产品的限制优先于“未复核可内部验证”的泛化表述；在WP2-00形成v1.3逐产品结论前，不把UNKNOWN自动改成“自用许可”。可推进不访问受限数据的代码和离线契约工作，现场调用和落库按该操作的实际许可放行。

## 5. 明确范围边界

保留单API worker部署。实时流、交易下单、OpenBB Desktop、原OpenBB发行包兼容运行时、PyPI发布、DWS/ADS和多worker重构未纳入本迭代。静态或延迟Quote/OptionsChains等固定模型可实现为请求型查询，不能顺带扩张为实时转发服务。

350条功能的开发需求已经明确；底层源的Key、访问条件或用途限制可能影响真实验收，不因此跳过可独立完成的实现。实际通知、正式数据库变更、旧表删除或外部发布仍以各动作既有授权和可审阅执行清单为准；编制计划不执行这些动作。
